## 成功因素

### 1. Phase 0 前置调查价值高

Story 4-1 先清理死依赖（jsoup、flexmark）+ 验证 md_content 空值频率，给后续 story 提供了数据驱动的决策依据。零空值结论直接支撑了 4-1a 降级链删除的安全性。

### 2. 4-1a 范围拆分合理

降级链删除 + filename 校验从 4-1 中独立出来，职责清晰。`extractReaderMarkdown()` 从 ~40 行降级逻辑压缩到 ~10 行直读逻辑，是 Epic 4 最显著的代码简化。

### 3. 4-3 实时决策正确

原计划重建 5 个 Docling 基线黄金样本。spike 在开发过程中发现 Docling 输出质量已达标，果断从"重建"改为"删除"。5 条理由充分：Docling 输出稳定、原测试仅含 README 结构校验无行为断言、现有 45 个单测覆盖充分。

### 4. Micrometer 指标实现干净

4-2 在 Parser 和 Chunker 两个 adapter 内部完成埋点，不引入额外间接层。Timer 动态标签（format）用运行时查找，Counter 静态标签用构造器预注册——设计合理。5 个新测试覆盖所有指标路径。

### 5. 测试全程稳定

4 个 story，测试从 490 → 492 → 497 → 493，零失败贯穿始终。

### 6. 行动项全部清零

Epic 1-4 积累的 26 个行动项全部有了明确结论：11 项完成、12 项正式关闭、1 项归属独立计划、2 项合并处理。

## 挑战与改进点

### 1. 长期推迟的行动项

Arconia 版本升级评估被提了 3 次（Epic 1/2/3），每次都推迟。markFailed null 测试和 @Disabled 审计跨 4 个 Epic 未处理。**教训：** 行动项要么排期执行，要么正式关闭并记录理由，不能无限推迟。

### 2. Story 4-3 范围大幅变更

原计划"重建黄金样本"，实际执行"删除黄金样本"。方向调整基于开发中的实际发现，决策正确，但说明 Epic 规划时对 Docling 输出质量的假设偏保守。
