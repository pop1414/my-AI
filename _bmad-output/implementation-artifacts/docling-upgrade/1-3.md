# Story 1.3: Actuator Health 检测 Docling 连通性

Status: ready-for-dev

## Story

As a 系统运维者，
I want Actuator health 能检测 Docling 连通性，
So that Docling 不可用时系统状态变为 DOWN，快速定位解析故障。

## Acceptance Criteria

1. Given Arconia Docling BOM 已引入（Story 1.2），DoclingServeApi Bean 已注入，When 访问 `/actuator/health` 端点，Then 响应包含 `docling` 组件的健康状态（`show-details` 已启用）。
2. 当 docling-serve 服务正常运行时，`docling` 组件状态为 `UP`。
3. 当 docling-serve 服务停止或不可达时，`docling` 组件状态变为 `DOWN`，整体 health 可能受影响。
4. 健康检查响应时间 ≤ 5 秒（由 `arconia.docling.connect-timeout: 5s` 控制）。
5. 首次启动时，若 Docling 不可用，系统应 fail-fast（应用启动失败，不进入就绪状态），输出明确的错误消息指向 Docling Serve 配置。

### Fail-fast 实现方案

Arconia **不提供**应用级 fail-fast 机制。需自定义实现。

**方案：SmartLifecycle + FailureAnalyzer**

```
应用启动 → Spring 容器初始化 → Bean 创建完成
→ SmartLifecycle.start() 阶段 → DoclingStartupVerifier.start()
→ 调用 DoclingServeApi.health()
→ 成功: 继续启动内嵌服务器
→ 失败: 抛出 DoclingUnavailableException
→ FailureAnalyzer 捕获 → 输出友好错误消息 → 应用退出
```

**为什么选择 SmartLifecycle 而非 @PostConstruct 或 ApplicationRunner：**
- `@PostConstruct` 在单个 Bean 初始化时执行，无法保证在所有 ingest 组件之后执行
- `ApplicationRunner` 在应用完全启动**之后**执行，此时内嵌服务器已就绪，fail-fast 太晚
- `SmartLifecycle` 在所有 Bean 初始化完成后、内嵌服务器启动前执行，是最合适的拦截点
- `getPhase()` 返回较大值确保在其他 Lifecycle Bean 之后执行

**DoclingServeApi.health() 方法签名：**
```java
HealthCheckResponse health = doclingServeApi.health();
// HealthCheckResponse 包含 status 字段，"ok" 表示健康
```

**错误处理注意：** `DoclingServeApi.health()` 在连接失败时会抛出以下异常（均需捕获）：
- `org.springframework.web.client.HttpClientErrorException`（4xx）
- `org.springframework.web.client.HttpServerErrorException`（5xx）
- `org.springframework.web.client.ResourceAccessException`（连接超时/网络不可达）

### DoclingUnavailableException 位置

此异常属于**启动校验**用途，不是 domain 层的 DoclingParseException 层次（那是运行时解析错误，属于 Story 2.4）。

```
DoclingUnavailableException extends IllegalStateException    ← 启动校验，infrastructure/config/
DoclingParseException extends RuntimeException              ← 运行时解析错误，domain/model/（Story 2.4）
```

两者互不依赖，不要混淆。
