# Decision Log: PRD Ingest 并发处理 + 批量上传 + 前端体验升级

> 追踪 PRD 创建过程中的每个决策

---

## 2026-06-20

### D-001: PRD 定级
- **决定**: Portfolio / 展示级别
- **理由**: 项目定位为展示工程能力的 portfolio 项目
- **影响**: PRD 需体现专业度（完整的需求编号、成功指标、风险分析）

### D-002: 工作模式
- **决定**: Fast path
- **理由**: spike 已有完整 SPEC + decision register + 讨论记录，输入材料充分

### D-003: PRD 存放位置
- **决定**: `_bmad-output/planning-artifacts/ingest-concurrent-processing/`
- **理由**: 与 SPEC 同目录，关联文档集中管理

### D-004: 批量 API 端点排期
- **决定**: MVP 不做 `POST /upload/batch`，前端循环调用现有单文件 API
- **理由**: 减少后端改动范围，前端并发队列已控制并发度为 3，对服务端压力可控
- **来源**: SPEC 第 3 节

### D-005: Worker 层不做超时
- **决定**: 超时由 Docling client `read-timeout: 30s` + `RetryPolicy` 覆盖
- **理由**: Virtual Thread 中断不能中断 I/O，Worker 层超时是多余防线
- **来源**: Winston 架构评审

### D-006: 前端并发队列不引入外部依赖
- **决定**: 用原生 Promise + 计数器实现（~20 LOC）
- **理由**: spike 建议，并发度仅 3-4，复杂度不值得引入 p-limit
- **来源**: spike 建议 1

### D-007: 条件轮询策略
- **决定**: 当前页存在 UPLOADED/INGESTING 文档时轮询（3s），否则停止
- **理由**: 避免无后台任务时的无意义请求
- **来源**: spike 建议 2

### D-008: documentId 展示策略
- **决定**: 上传成功/失败均展示 documentId（可复制），列表页失败行 Tooltip 展示
- **理由**: 运维排障效率——用户复制 documentId 给运维，Kibana 一秒定位日志
- **来源**: spike 建议 3

### D-009: 状态摘要栏统计范围
- **决定**: 全库统计，不受筛选条件影响
- **理由**: 摘要栏的价值是"系统整体概览"，筛选条件变了数字跟着变反而让人困惑

### D-010: 快速重试按钮权限
- **决定**: 所有用户可见，只要对 KB 有写权限即可重试
- **理由**: 复用现有 `canContributeKnowledgeBase` 权限校验，无需新增逻辑；团队协作场景下帮忙重试合理

### D-011: 状态更新方式
- **决定**: 3s 轮询（React Query refetchInterval），不引入 WebSocket/SSE
- **理由**: 单实例、单用户场景，3s 延迟完全可接受，复杂度为零

### D-012: parallelism 调优策略
- **决定**: 默认值 3，上线后根据 Docling Serve CPU/内存和处理延迟观察调优
- **理由**: 运行时可配（环境变量），MVP 阶段不值得做压力测试
