## 最终结论

### 核心定位

> **"面向企业内部文档的私有化 AI 阅读助手"**

公司文档有权限分级，员工只能在自己授权范围内用 AI 提问和阅读。数据不出企业内网。

### 场景来源

Spike 实习时的真实痛点：公司内部文件保密，不能用外部 AI 工具，但员工需要高效阅读文档，且只能看自己部门+公司公开的文档。需要一个带权限控制的私有化 AI 阅读系统。

### 三个差异化锚点

1. **权限驱动的 AI 检索** — 你能问的，取决于你能看的。检索阶段就必须按权限过滤，不能"先检索再裁剪"（ADR-0005 硬约束）
2. **私有化部署** — 数据不出企业内网，支持本地模型（Ollama），不强制依赖外部 AI 服务
3. **文档处理质量** — 不是 demo 级别，是真能用来读公司真实文档的

### 面试叙事

> "我在实习时发现公司内部文档管理有个问题：文件保密不能用外部 AI，但人工阅读效率很低，而且每个人只能看自己权限范围内的文档。所以我做了这个项目——一个带权限控制的私有化文档 AI 阅读系统。"

## 权限模型：从三级树 → 群组模型 (Group Model)

### 为什么换

当前 Workspace → KnowledgeBase → Document 是树形结构，一个人只能归属一个 Workspace。实习场景的真实情况是：一个人同时属于技术部、项目X、全员公告等多个"圈子"，每个圈子的文档和权限不同。树形模型装不下这个现实。

### 新模型

```
Workspace（公司/租户边界）
  ├── User（可加入多个 Group）
  ├── Group（群组：部门 / 项目 / 自定义圈子）
  │     └── DocumentGroup（文档分配到哪些 Group）
  └── Document（文档资产，版本链、处理状态不变）
```

### 四个关键设计决策

#### 1. 上传摩擦：零 Group = 草稿区

文档上传后可以不挂任何 Group（`document_groups` 无记录）。

可见规则：

- 零 Group 的文档只有**上传者**和 **Workspace Admin** 可见
- 挂上第一个 Group 后进入正常权限体系
- Admin 界面提供"未分配文档"视图，防止零 Group 文档从管理视角消失

检索范围公式：

```
用户可见文档 =
  { 用户所在 ACTIVE Group 的文档 }
  ∪ { 上传者是当前用户 且 零 Group 的文档 }
  ∪ { DOC_ALLOW 覆盖的文档 }
  - { DOC_DENY 排除的文档 }
```

**选择理由**：不引入"个人 Group"或"草稿"等额外概念。用"无 Group"本身表示草稿区，代码路径清晰。

#### 2. Group 创建与成员管理

**创建**：任何已验证用户可建 Group，创建者自动成为第一个 MANAGER。

**成员邀请**：

```
MANAGER 发起邀请 → status = PENDING → 被邀请人收到通知
  → 接受 → status = ACTIVE → 检索范围生效
  → 拒绝 → 记录删除
Workspace Admin 直接操作 → 跳过确认，直接 ACTIVE
```

**为什么邀请需要确认**：Group 成员资格直接扩大用户的检索范围（可以看到该 Group 下的文档），被邀请人必须主动接受，不能被动加入。

#### 3. 跨 Group 文档权限：Highest Wins

一个文档属于多个 Group，用户在不同 Group 里角色不同时，取最高角色。

```
文档"API设计"属于：技术部（READER）+ 项目X（CONTRIBUTOR）
用户权限 = max(READER, CONTRIBUTOR) = CONTRIBUTOR
```

**选择理由**：如果项目X需要你编辑这份文档，技术部的只读角色不应该阻止。最宽权限胜出。

`document_groups` 表预留 `minRole` 字段（建表时有列，v1 无使用逻辑）。将来需要"这份合同在技术部 Group 里只能看不能改"时，激活 minRole 即可，不需要 migrate 表结构。

#### 4. 检索性能

当前代码 chunk metadata 已有 `documentId`（`PgVectorDocumentVectorIndexer.java:107`），检索时按可见文档 ID 集合过滤。

**立刻需要做的**：

- 加 GIN 索引：`CREATE INDEX ON vector_store USING GIN ((metadata -> 'documentId'))`
- 检索改写：N 个 OR 分支改为 `WHERE metadata->>'documentId' = ANY(:visibleDocIds)`

**数量级估算**：用户 15 个 Group × 200 文档/Group = 最多 3000 个 documentId，去重后约 1000-2000。`ANY(array)` 完全够用，临界点在 10000+ documentId 时才需要 Redis 缓存或临时表 JOIN 方案。

### 与现有代码的变更量

```
新增表: groups, user_groups, document_groups
取代: knowledge_base_grants → user_groups.role 替代
移除: KnowledgeBase 实体 → Group 替代
保留: document_grants (DOC_ALLOW/DOC_DENY), workspace_memberships
修改: ingest_documents.kb_id → 改为可选，通过 document_groups 关联
```
