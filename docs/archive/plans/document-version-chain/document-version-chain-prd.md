# PRD：文档版本链与治理基线

## Problem Statement

当前系统已经具备文档上传、处理、重处理、删除、知识库问答和权限治理基础能力，但 `document` 仍主要以单条记录承载文档资产、处理状态、重试上下文和分块版本。用户现在需要围绕同一 `document` 进行“上传新版本、查看版本历史、版本回退、删除后重新上传、按可问答版本参与问答”的完整治理流程，但当前实现缺少稳定的版本链 module，导致问答基线、版本治理动作、历史版本可见性和审计定位都无法以清晰且可测试的方式落地。

## Solution

将 `document` 从“单条记录承载全部版本事实”的实现，演进为“`document` 主表 + `document version` 子表”的版本链方案。对用户来说，这意味着系统能够稳定支持同一文档资产的线性版本演进：用户可在文档详情页上传新版本、查看版本历史、将历史版本回退为新的最新版本，并在最新版本尚未 `INDEXED` 时继续基于最近一个已 `INDEXED` 的版本进行问答。系统会明确展示版本来源、版本状态和当前问答基线，并对删除、回退、上传新版本等治理动作提供一致的权限、并发校验、审计和结果提示。

## User Stories

1. 作为 `KB_MANAGER`，我希望能在既有 `document` 的详情页发起上传新版本，这样内容变化就可以继续沿用同一个 `documentId` 演进。
2. 作为具备 `DOC_ALLOW_MANAGE` 的用户，我希望上传新版本时锁定当前 `knowledge base`，这样我就不会误把 `document` 移动到别的业务边界。
3. 作为文档管理者，我希望当上传的新版本内容与当前最新版本完全相同时，系统按复用处理而不是创建新版本，这样版本链才不会被无意义重复版本污染。
4. 作为文档管理者，我希望上传新版本成功后能看到新版本号和上一版本号，这样我能确认版本链确实按预期前进。
5. 作为文档管理者，我希望上传新版本成功后页面上有稳定的结果提示区，这样我可以继续查看版本历史或去问答，而不是依赖瞬时消息。
6. 作为文档管理者，我希望当当前最新版本处于 `UPLOADED` 或 `INGESTING` 时，上传新版本请求会被拒绝，这样并发治理动作不会制造不明确的最新版本状态。
7. 作为文档管理者，我希望当当前最新版本处于 `FAILED` 时，系统仍允许上传新版本，这样我可以用新的源文件恢复失败的最新内容。
8. 作为文档管理者，我希望版本历史始终挂在同一个 `document` 下，这样我能持续审计同一文档资产的演进过程。
9. 作为文档管理者，我希望版本历史列表项展示版本号、来源文件名、上传人、上传时间、状态以及当前是否可用于问答，这样我能同时理解治理上下文和问答上下文。
10. 作为文档管理者，我希望普通用户在没有管理权限时看不到旧版本，这样治理视角的上下文就不会泄漏给不该看到的人。
11. 作为文档管理者，我希望切换查看历史版本时不会改变系统当前的可问答版本，这样查看行为不会影响运行时问答结果。
12. 作为文档管理者，我希望查看历史版本时系统明确提示“当前查看的不是最新版本”，这样我不会把审计查看误认为当前生产态。
13. 作为文档管理者，我希望历史版本默认与当前最新版本做差异比较，这样我在决定是否回退前能直接判断改动内容。
14. 作为文档管理者，我希望版本回退是“创建一个新的最新版本”，而不是回拨版本指针，这样版本链才能保持线性且可审计。
15. 作为文档管理者，我希望只能将已经形成可用内容的历史版本作为回退目标，这样我不会把不可用的历史状态提升为最新版本。
16. 作为文档管理者，我希望回退确认明确告知“会创建新的最新版本”且“可能改变问答基线”，这样我能理解下游影响。
17. 作为文档管理者，我希望回退成功后能看到新最新版本号和回退目标版本号，这样我能核对新旧版本关系。
18. 作为文档管理者，我希望由回退产生的新最新版本重新从 `UPLOADED` 进入 ingest 处理链路，这样它与正常上传新版本保持一致的处理语义。
19. 作为文档管理者，我希望即使回退产生的新最新版本后续处理成 `FAILED`，它仍保留“当前最新版本”的语义，这样版本链事实不会被静默改写。
20. 作为问答用户，我希望 `qa` 对每个 `document` 独立决定当前可问答版本，这样一次回答就能安全地组合多个处于不同最新版本状态的文档来源。
21. 作为问答用户，我希望当最新版本尚不可问答时，`qa` 继续使用最近一个已 `INDEXED` 的版本，这样文档更新不会造成不必要的问答中断。
22. 作为问答用户，我希望每条引用都展示来源版本号、来源更新时间、是否为最新版本以及当前最新版本号，这样我能准确判断引用是否过期。
23. 作为问答用户，我希望只有当至少一条引用不是对应 `document` 的最新版本时，问答页顶部才展示 stale reference 汇总提示，这样版本提示才是精确而不是噪音。
24. 作为问答用户，我希望当一次问答没有任何文档引用、仅返回模型兜底内容时，不展示版本提示，这样系统不会制造虚假的可追溯感。
25. 作为文档管理者，我希望文档列表页与详情页的主视图始终锚定当前最新版本，即使问答仍在使用旧的已索引版本，这样治理状态与问答基线不会混淆。
26. 作为文档管理者，我希望文档列表展示最新版本的真实状态和最新来源文件名，这样列表视图反映的就是当前文档资产事实。
27. 作为文档管理者，我希望删除确认明确提示“删除后同内容重新上传会生成新的 `documentId`”，这样我能理解文档身份断裂的后果。
28. 作为文档管理者，我希望删除确认要求手动输入完整 `documentId`，这样高风险治理动作有足够的操作摩擦。
29. 作为文档管理者，我希望删除成功后的结果提示明确说明文档级授权不会自动继承到新的 `document`，这样我不会误判后续授权状态。
30. 作为工作区管理员，我希望上传新版本、版本回退、重处理和删除在同一 `document` 上互斥进入执行态，这样任一时刻只会有一个治理动作真正生效。
31. 作为前端用户，我希望文档详情页的治理结果提示保持稳定可见，直到我主动处理或离开页面，这样关键结果不会丢失。
32. 作为审计查看者，我希望上传新版本和版本回退分别记录独立审计事件，并附带版本上下文，这样后续能重建治理决策过程。
33. 作为工程维护者，我希望把 `document` 身份、`document version` 事实和处理尝试轨迹拆成更清晰的 modules，这样代码库会更可测试，也更容易演进。

## Implementation Decisions

- 引入一个深一点的 `document version chain` module，把稳定的 `document` 身份与版本级文件事实、处理事实、版本来源事实拆开。
- 保留 `document` 作为稳定资产身份和最新版本轻量投影；把版本级文件元数据、状态、失败上下文与 `processingMetadata` 下沉到 `document version`。
- 版本链保持单条线性链。上传新版本始终从当前最新版本向前推进；历史版本不能直接分叉生成新上传版本。
- 版本回退建模为创建一个 `versionOriginType = ROLLBACK` 的新最新版本，而不是回拨版本指针。
- `askable` 保持为运行时推导规则，而不是持久化字段。当前可问答版本由版本状态和“最新版本未可问答时回退到最近一个已 `INDEXED` 版本”的规则共同推导。
- 保持现有 `knowledge base` 归属规则：每个 `document` 只属于一个 `knowledge base`，上传新版本不允许改变该绑定。
- 上传新版本和版本回退都引入 `expectedLatestVersionNumber` 一类的乐观并发校验。
- 当上传新版本命中同内容复用时，按成功分支处理，复用当前最新版本，不创建新版本。
- 删除仍建模为终止整个 `document` 资产，而不是删除某个版本；软删除后的 `document` 仍保留终态与审计上下文可查询。
- 删除完成前后区分两类身份边界：`DELETING` 期间同内容上传仍命中原 `documentId`，避免与当前 `(kb_id, file_hash)` 兼容唯一索引冲突；只有旧 document 到达 `DELETED` 终态后，同内容重新上传才生成新的 `documentId`，且旧 document 的文档级授权不自动继承到新 document。
- 文档列表与详情主视图锚定 latest projection：列表展示 `latest_filename/latest_status/latest_version_number/latest_version_origin_type` 与最新版本事实，详情状态查询展示当前最新版本的状态、来源文件名和版本来源类型。
- 删除、上传新版本、版本回退和重处理在同一 `document` 上按执行态互斥：`UPLOADED`、`INGESTING`、`DELETING` 期间不再允许删除插入执行态；上传新版本、版本回退和重处理继续依赖 latest 状态与乐观并发校验。
- 为上传新版本和版本回退定义带版本上下文的专用成功结果 DTO，显式返回当前最新版本和当前可问答版本。
- 扩展 `qa` 引用契约，补充版本来源字段和 stale reference 汇总字段，同时保持 `qa` 只消费当前用户有权访问内容的规则不变。
- 保持 ADR-0005 的安全约束：不能先越权召回，再靠展示层裁剪引用。
- 版本历史可见性以及版本治理动作仅对具备目标 `document` 管理权限的用户开放。
- `processingMetadata` 继续作为文档处理结果元数据，服务于追踪、调试和分块参考，不提升为前端业务主数据。
- schema 演进按阶段推进：先落 `document` 与 `document version`，后续当重试与执行轨迹复杂度继续上升时，再把 `processing attempt` 抽成独立 seam。
- 主要需要调整的 modules 包括 ingest 应用服务、ingest 持久化、QA 应用服务、治理相关 REST 契约、前端文档详情/列表流转和审计事件写入。

## Testing Decisions

- 好测试应围绕外部行为与稳定业务规则展开：版本链推进、版本回退语义、可问答版本推导、权限门禁、乐观并发冲突拒绝、引用版本来源输出，而不是锁死在某个持久化实现细节或 UI 实现细节上。
- 后端测试应覆盖深一点的 `document version chain` module、ingest 治理应用服务、QA 可问答版本选择行为、审计事件写入和 schema 演进后的持久化 adapter。
- 前端测试应覆盖文档详情治理流、版本历史可见性、回退/删除确认、稳定结果提示区以及问答页版本提示行为。
- 代码库里的 prior art 包括 ingest 应用服务测试、JDBC repository 测试、QA 应用服务测试、REST controller 测试和 auth 治理测试；新测试应优先沿用这些已有测试风格，而不是另起一套。
- 回归覆盖至少应包含：最新版本未 `INDEXED`、最新版本 `FAILED`、回退产生的新最新版本再次 `FAILED`、同内容复用不创建新版本、过期页面触发的最新版本并发冲突，以及治理动作互斥。

## Out of Scope

- OCR 与复杂版式增强。
- 多工作区或多租户演进。
- OIDC、SSO 或机器身份集成。
- Chat 或 Embedding Provider 的切换。
- 用全新检索架构替换当前 chunking 策略。
- 若 `document` 与 `document version` 已形成稳定 seam，则首期不强行抽出完整 `processing attempt` 表。
- 权限拒绝后的复杂审批流；当前阶段只保留“联系管理员”指引。

## Further Notes

- 本 PRD 严格沿用 `CONTEXT.md` 中的领域词汇；`workspace`、`knowledge base`、`document`、`document version`、`processingMetadata`、`INDEXED`、`FAILED`、`DOC_ALLOW_MANAGE`、`KB_MANAGER` 等术语保持权威。
- 当实现与文档不一致时，已采纳 ADR 和当前主文档优先于现状代码实现。
- 当前目标分支是 `feature/document-version-chain`，该计划应以“不重新定义 RAG 质量优化分支的职责边界”为前提推进。
