## 01-知识库主数据化（修订版）

### 摘要

把当前基于 `ingest_documents.kb_id` 聚合出来的“字符串知识库”升级为正式主数据。数据库层引入自增主键 `id` 和唯一业务键 `kb_id`；服务端生成对外 `kb_id`，用户只管理 `name/description/status`。首版支持 `创建 + 列表 + 编辑`，不做删除；保留 `default` 兼容历史数据与空值回退。

### 关键实现

- 新增 `knowledge_bases` 主数据表：
    - `id`：数据库自增主键，仅内部使用
    - `kb_id`：唯一业务键，服务端生成，API 路径与响应对外使用它
    - `name`
    - `description`
    - `status`
    - `created_at`
    - `updated_at`
- `kb_id` 生成策略固定为 `UUID`；前端和 API 不暴露数据库自增主键。
- 现有 `ingest_documents.kb_id` 继续保留，作为与知识库主数据的业务关联字段；V1.1 不改写旧文档的 `documentId` 规则，也不引入新的外键主键暴露方式。
- 知识库首版动作：
    - `POST /api/v1/knowledge-bases`：创建知识库，服务端生成 `kb_id`
    - `GET /api/v1/knowledge-bases`：查询知识库列表
    - `PATCH /api/v1/knowledge-bases/{kbId}`：修改 `name/description/status`
- 第一版不做知识库删除；停用通过 `status=INACTIVE` 表达。
- 上传和问答主路径继续支持空 `kbId -> default` 回退，但如果显式传入了不存在或已停用的 `kbId`，必须阻断：
    - 不存在：`400`
    - 已停用：`409`
- 前端上传页和问答页改为“知识库下拉选择为主”；选项只展示 `ACTIVE` 知识库。知识库管理页自身展示全部知识库，并显示状态与统计。

### 接口与字段约束

- 创建请求：
    - `POST /api/v1/knowledge-bases`
    - 请求体：`name` 必填，`description` 可选，`status` 可选且默认 `ACTIVE`
    - 不接收客户端传入的 `kb_id`
- 编辑请求：
    - `PATCH /api/v1/knowledge-bases/{kbId}`
    - 允许修改：`name`、`description`、`status`
- 列表响应：
    - 保持兼容：继续返回现有 `id`、`name`、`indexedDocumentCount`
    - 纯新增字段：补充 `description`、`status`
    - 不删除、不重命名任何现有字段
    - `id` 继续表示对外业务键 `kb_id`
- 字段规则固定如下：
    - `id`（响应中的 `kb_id`）：服务端生成，输出值为字符串；采用 UUID；数据库唯一；客户端 `POST` 不传
    - `name`：必填，`1~100` 字符，不允许纯空白
    - `description`：可选，`0~500` 字符
    - `status`：可选，默认 `ACTIVE`；只允许 `ACTIVE` 或 `INACTIVE`
- `GET /api/v1/knowledge-bases` 的语义从“仅统计聚合”升级为“主数据 + 统计视图”：
    - 返回所有知识库，包括 `0` 文档知识库和 `INACTIVE` 知识库
    - `indexedDocumentCount` 仍只统计 `status=INDEXED` 的文档数量

### 历史数据迁移与兼容

- 升级脚本必须是幂等的，并在旧环境升级时执行两步回填：
    1. 插入 `default` 知识库；如已存在则跳过
    2. 从 `ingest_documents` 提取所有 `DISTINCT kb_id`；对每个在 `knowledge_bases` 中不存在的值，自动插入一条记录，规则为：
        - `kb_id`：沿用旧值
        - `name`：默认等于 `kb_id`
        - `description`：空
        - `status`：`ACTIVE`
- 这样可以确保升级后历史文档引用的 `kb_id` 都能在主数据表中命中，避免上传/问答链路因校验升级而直接 `400`
- 新环境初始化规则：
    - 自动创建 `default`
    - 不需要额外历史回填数据时也可正常启动

### 测试计划

- 主数据层：
    - `knowledge_bases` 建表成功，`kb_id` 唯一约束生效
    - 新建环境自动创建 `default`
    - 旧环境迁移后，`ingest_documents` 中已有的 `kb_id` 全部能回填到主数据表
- 接口行为：
    - `POST` 不接受客户端 `id`，成功后返回服务端生成的 `id`
    - `PATCH` 可修改 `name/description/status`
    - `GET` 保留 `id/name/indexedDocumentCount`，并新增 `description/status`
    - 新建但尚无文档的知识库也能在列表中看到，`indexedDocumentCount=0`
- 兼容行为：
    - 上传/问答空 `kbId` 仍回退到 `default`
    - 上传/问答传不存在的 `kbId` 返回 `400`
    - 上传/问答传 `INACTIVE` 的 `kbId` 返回 `409`
- 前端：
    - 上传页和问答页能正确加载 `ACTIVE` 知识库下拉项
    - `INACTIVE` 知识库不出现在上传/问答选择器中
    - 知识库管理页能展示全部知识库及其状态

### 假设与默认值

- `kb_id` 使用标准 UUID 作为第一版默认生成规则，不引入短 ID 或自定义编码。
- 数据库内部自增 `id` 只用于存储层，不出现在外部 API。
- 第一版不做知识库删除、不做知识库与文档的解绑迁移、不做批量停用。
- 历史回填生成的知识库默认 `name=kb_id`，后续可通过 `PATCH` 逐步改名。
