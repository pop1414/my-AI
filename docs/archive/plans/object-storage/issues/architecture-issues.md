我按 `improve-codebase-architecture` 看了一轮。结论：RustFS 这轮大方向符合 ADR-0007，`domain/application` 没直接依赖 AWS SDK，`source` 和 `artifacts` 也保持了两个真实 adapter。但有几个需要注意的 architecture friction，按优先级排：

1. **首传 source 持久化还在 Controller 里，S3 会放大一致性问题**Files: [DocumentIngestController.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/interfaces/rest/DocumentIngestController.java:257), [AcceptUploadApplicationService.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/application/service/AcceptUploadApplicationService.java:1)Problem: `acceptUploadUseCase.handle(...)` 先创建 DB 事实，Controller 再调用 `documentSourceStorage.save(...)`。这让上传用例的 interface 没有完整表达“受理上传必须同时形成 source”。RustFS 不可用时，可能留下 `UPLOADED` document 但 source 缺失。Solution: 后续应把“创建 document/version fact + 保存 source + 失败补偿/状态语义”收进 application upload module，由用例统一拥有。Controller 只负责 HTTP 到 command 的转换。Benefit: locality 更好，上传一致性、审计、失败语义集中在一个 module；测试也能直接覆盖 RustFS 失败时是否留下半成品。
2. **`DocumentSourceStorage` 的 workspace seam 不完整**Files: [DocumentSourceStorage.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/domain/port/DocumentSourceStorage.java:57), [S3DocumentSourceStorage.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/infrastructure/storage/S3DocumentSourceStorage.java:108)Problem: ADR-0007 的 source key 包含 `workspaceId`，但 source storage interface 只有 `documentId/version/filename`，S3 adapter 内部硬编码 `WorkspaceConstants.DEFAULT_WORKSPACE_ID`。当前单工作区可接受，但这个 interface 已经和 key invariant 不完全一致。Solution: 下一步多 workspace 或迁移前，考虑引入 `DocumentAssetLocation` / `DocumentVersionAssetRef` 这类值对象，统一承载 `workspaceId + documentId + versionNumber + filename/artifactName`。Benefit: source/artifact key 规则更 deep，caller 不需要猜哪些 adapter 会默认 workspace；后续多工作区不会散点改签名。
3. **storage 冲突语义靠字符串 message 穿透**Files: [DocumentSourceStorage.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/domain/port/DocumentSourceStorage.java:18), [UploadNewDocumentVersionApplicationService.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/application/service/UploadNewDocumentVersionApplicationService.java:279), [RollbackDocumentVersionApplicationService.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/application/service/RollbackDocumentVersionApplicationService.java:261)Problem: application 层用 `IllegalStateException.getMessage()` 判断 `version source file content conflict`。这让 interface 的 error mode 很脆，adapter 改 message 就破坏业务映射。Solution: 提取稳定异常类型，例如 `DocumentSourceContentConflictException`，由 local/S3 adapters 共同抛出。Benefit: interface 是测试面；用类型表达错误模式后，测试和调用方都更清晰。
4. **S3 object 操作细节在两个 adapter 里重复**Files: [S3DocumentSourceStorage.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/infrastructure/storage/S3DocumentSourceStorage.java:135), [S3DocumentProcessingArtifactStorage.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/infrastructure/storage/S3DocumentProcessingArtifactStorage.java:174)Problem: `isObjectNotFound`、分页删除、批量 delete、head/get 这类 S3 语义重复存在。现在重复量还可控，但一旦加 backup、migration、health check，错误映射会分叉。Solution: 只在 infrastructure 内部抽一个 `S3ObjectStore` helper，不上升为 domain port。它负责 `exists/loadBytes/loadText/put/listDeletePrefix/notFoundMapping`。Benefit: locality 更强，S3 兼容差异只在一个 implementation 里处理；source/artifact adapters 继续保持业务 prefix 语义。
5. **主配置里带 S3 默认凭证，削弱 fail-fast 配置语义**File: [application.yaml](D:/Code/project/my-AI/src/main/resources/application.yaml:72)Problem: `IngestProperties` 默认 access/secret 是空，但 `application.yaml` 给了 `admin/Admin@123`。这对本地方便，但 `INGEST_STORAGE_TYPE=s3` 时即使没注入凭证也不会 fail fast。Solution: 更稳的做法是主配置保持空值，本地 profile 或 runbook 示例提供 `admin/Admin@123`。Benefit: release 配置 interface 更清楚，生产/共享环境不会意外使用本地默认凭证。
6. **删除对象结果没有显式检查 partial failure**
   Files: [S3DocumentSourceStorage.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/infrastructure/storage/S3DocumentSourceStorage.java:181), [S3DocumentProcessingArtifactStorage.java](D:/Code/project/my-AI/src/main/java/io/github/spike/myai/ingest/infrastructure/storage/S3DocumentProcessingArtifactStorage.java:168)
   Problem: `deleteObjects(...)` 的 response 没检查 errors。对 RustFS 可能没问题，但 S3-compatible 目标扩展后，partial delete 需要明确失败，否则 `DELETED` 状态可能掩盖残留对象。
   Solution: 在 S3 helper 或 adapter 中检查 delete response errors，非空就抛基础设施异常，让 `DeleteDocumentApplicationService` 保持回滚删除状态。
   Benefit: 删除 module 的 interface 更可信，source/artifacts 清理不会静默漏对象。

我建议优先深挖 **1：上传受理 module 收口**。这是 RustFS 引入后最容易从“本地文件系统小概率 IO 异常”升级成“远端对象存储常见基础设施失败”的地方。其次是 **2 + 3**，它们会决定后面历史迁移和多 workspace 是否好做。
