# RAG 权限体系 - 知识库列表授权可见性收紧实施计划

日期：2026-05-11  
状态：Completed  
主题归属：`rag-access-control` 专项  
范围边界：后端优先，仅收紧知识库列表可见范围，不改前端接口结构

## 1. 背景

在知识库主数据、知识库授权治理和业务权限接入完成后，
`GET /api/v1/knowledge-bases` 仍保留了一个不够严格的行为：

- 当前工作区管理员和普通成员都按工作区范围获取知识库列表
- 普通成员即使没有某个知识库的显式授权，也可能看到该知识库的元数据

这会造成两个问题：

1. 列表可见性和真实访问权限边界不一致
2. 普通成员可能提前感知自己无权访问的知识库名称、描述和统计信息

因此需要把“能否看到知识库”单独收口成显式规则。

## 2. 本轮目标

本轮只解决知识库列表可见性问题，规则固定为：

- `WORKSPACE_OWNER / WORKSPACE_ADMIN`
  - 可见当前工作区全部知识库
- `WORKSPACE_MEMBER`
  - 仅可见自己存在 `ACTIVE` 显式知识库授权的知识库

## 3. 本轮不做什么

- 不修改知识库详情 / 编辑 / 创建接口语义
- 不引入新的前端字段或响应结构
- 不在本轮把文档级授权反推到知识库列表可见性
- 不处理前端知识库列表页和知识库选择器的交互优化

## 4. 技术策略

### 4.1 改动位置

本轮将可见性规则放在应用层，而不是控制器层。

原因：

- 控制器只负责 HTTP 形态，不应该承载授权决策
- 可见性规则本质上是业务访问规则，适合落在应用服务

### 4.2 复用现有授权真源

直接复用：

- `knowledge_base_grants`

并通过授权读取端口补一个“当前用户已授权知识库集合”的查询能力。

### 4.3 保持接口契约稳定

本轮不修改：

- 接口路径
- 响应字段
- 前端调用方式

只调整普通成员实际能拿到的条目集合。

## 5. 实施拆解

### 5.1 授权端口

在 `AuthorizationGrantRepository` 中新增：

- `listGrantedKnowledgeBaseIds(workspaceId, userId)`

职责：

- 返回当前用户在当前工作区内具备 `ACTIVE` 显式知识库授权的知识库 ID 集合

### 5.2 JDBC 实现

在 `JdbcAuthorizationGrantRepository` 中新增对应 SQL，实现：

- 按 `workspace_id + user_id + status = ACTIVE` 查询知识库 ID 集合

### 5.3 应用服务

在 `ListKnowledgeBasesApplicationService` 中补充可见性分流：

- 管理员：直接返回工作区全部知识库
- 普通成员：按授权集合过滤后返回

## 6. 验收标准

本轮完成时，至少满足：

1. 管理员查询知识库列表时仍返回工作区全部知识库
2. 普通成员查询知识库列表时只返回自己显式授权的知识库
3. 普通成员无任何知识库授权时返回空列表
4. 控制器接口与前端调用方式保持不变
5. API 契约文档同步更新可见性规则

## 7. 验证方式

本轮验证采用后端针对性测试：

- `ListKnowledgeBasesApplicationServiceTest`
- `KnowledgeBaseControllerTest`
- `AuthorizationServiceTest`
- `AuthSecurityBaselineTest`

执行命令：

```bash
.\mvnw.cmd -q "-Dtest=ListKnowledgeBasesApplicationServiceTest,KnowledgeBaseControllerTest,AuthorizationServiceTest,AuthSecurityBaselineTest" test
```

## 8. 当前结论

这批改动完成后，知识库列表已经从“工作区全量可见”收紧为“按当前用户授权可见”，
后续前端知识库页和知识库选择器可以直接复用这个更严格的后端边界。
