# my-AI 文档工作流

## 1. 这份文档是干什么的

这份文档用来规定 `my-AI` 项目里，文档应该如何参与开发流程。  
目标不是让文档变多，而是让文档：

1. 跟代码变化保持基本同步
2. 真正服务开发，而不是成为额外负担
3. 帮助未来的自己快速接手项目
4. 沉淀出可用于课程、答辩、面试的材料

一句话原则：

> 文档不是和代码并列的另一份工作，而是代码变化的记忆系统。

## 2. 文档分层与职责

在 `my-AI` 中，文档分为三层：

### 2.1 工程真源层：`docs/`

回答的问题是：

- 系统现在是什么
- 当前版本支持什么
- 接口是什么
- 架构和运行方式是什么

典型文档：

- `README.md`
- `docs/product/scope.md`
- `docs/product/roadmap.md`
- `docs/architecture/README.md`
- `docs/api/openapi.yaml`
- `docs/releases/release-notes.md`
- `docs/06-07` 专题设计
- `docs/runbooks/` 里的执行与联调手册

规则：

- 这里的文档默认描述**当前最新事实**
- 如果这里的内容过期，会直接误导开发和协作

### 2.2 学习沉淀层：`docs/learning/`

回答的问题是：

- 我为什么这样设计
- 我真正学到了什么
- 还有哪些替代方案
- 面试官可能会怎么追问

规则：

- 可以带主观复盘
- 可以记录踩坑
- 不能替代正式工程事实

### 2.3 课程交付层：`deliverables/course/`

回答的问题是：

- 这次课程要提交什么
- 给老师展示什么
- 最终 PDF / DOCX / 视频脚本放哪里

规则：

- 课程材料主要从工程真源整理导出
- 不并行维护另一套和工程真源冲突的事实

## 3. 文档类型与触发时机

以后不要问“要不要写文档”，而要问：

> 这次变化属于哪一种文档触发器？

### 3.1 计划文档

适用时机：

- 准备做一个新功能
- 准备开始一个阶段性收口
- 准备处理一个跨模块改动

应该写什么：

- 目标
- 范围
- 不做什么
- 验收标准
- 风险 / 依赖（如果有）

推荐位置：

- `docs/runbooks/plans/<version>/`

在 `my-AI` 中的例子：

- `docs/runbooks/plans/v1/v1-closure-plan.md`

### 3.2 事实文档

适用时机：

- 用户可见行为改变
- 接口改变
- 配置或运行方式改变
- 页面范围改变
- 当前版本边界改变

应该更新什么：

- `README.md`
- `docs/api/openapi.yaml`
- `docs/architecture/README.md`
- `web/README.md`
- `docs/runbooks/` 中的联调/演示说明

规则：

- 只写“当前必须知道的事实”
- 不在这里记录实现过程中的琐碎犹豫

### 3.3 决策文档（ADR）

适用时机：

- 做了关键技术选型
- 改变了架构边界
- 引入了会影响未来演进的重要策略

应该写什么：

- 背景
- 决策
- 为什么这么做
- 代价
- 后续影响

典型场景：

- 向量存储从简单本地方案切到 PGVector
- 引入权限模型
- 引入多租户
- worker 调度和重试策略定型
- 子域拆分

规则：

- 不是每个小实现细节都写 ADR
- 只有“未来会反复被问为什么”的决策才写

### 3.4 学习沉淀文档

适用时机：

- 做完一个重要功能
- 解决了一个你原本并不真正懂的问题
- 遇到了值得总结的坑
- 这个点很可能在面试里被深挖

应该写什么：

1. 背景 / 问题
2. 这次项目里我是怎么遇到它的
3. 我最后采用了什么方案
4. 为什么不用别的方案
5. 面试官可能怎么问
6. 我该怎么回答
7. 相关代码 / 文档入口

推荐位置：

- `docs/learning/`

## 4. 标准开发节奏

以后每做一个功能，都尽量遵循下面的最小闭环。

### 第 1 步：开工前先写一个小计划

不要求长，但必须写清：

- 做什么
- 为什么做
- 范围边界
- 不做什么
- 验收标准

建议文件位置：

- `docs/runbooks/xxx-plan.md`

规则：

- 开工前写“方向和边界”
- 不要在没做之前把实现细节写得像已经完成

### 第 2 步：编码过程中只记录“重要偏差”

实现通常不会完全按计划走。  
这时不要慌着重写全部文档，而是只记录真正重要的偏差。

应该记录的偏差：

- 原计划与实际方案不同
- 对外事实发生变化
- 关键架构决策改变

不需要记录的偏差：

- 内部 helper 拆法变化
- 小型重构
- 不影响外部行为的实现细节调整

推荐做法：

- 直接在计划文档下增加：
  - `Decision log`
  - `Changed during implementation`
  - `Open questions`

### 第 3 步：功能做完后更新真源文档

做完后最少要检查：

- `README.md`
- `docs/api/openapi.yaml`
- `docs/architecture/README.md`
- `web/README.md`
- 对应 runbook / 演示步骤

原则：

- 只更新别人理解这个系统必须知道的事实
- 不把“已经废弃的计划思路”写进正式事实文档

### 第 4 步：补一篇学习沉淀

每个重要功能尽量补一篇 learning 文档。  
它的意义不是凑数量，而是把“做过”变成“学会”。

优先补的主题：

- 你原来不理解、现在理解了的点
- 面试官一定会追问的点
- 你自己以后大概率会忘的设计原因

### 第 5 步：收口时做一次文档同步检查

在一个功能或一个迭代收口时，至少过一遍：

- README 说的功能真的存在吗
- API 契约和实现一致吗
- 页面说明和前端真实状态一致吗
- 本轮计划文档是否已经明显过期
- 这次是否需要 ADR
- 是否至少有一篇值得保留的 learning

## 5. 文档触发器清单

以后每次改代码，问自己下面 6 个问题：

1. 这次改动有没有改变用户可见行为？
2. 这次改动有没有改变接口？
3. 这次改动有没有改变架构边界？
4. 这次改动有没有改变运行方式、联调方式或排障方式？
5. 这次改动有没有做出重要取舍？
6. 这次改动有没有值得沉淀成“我真正学会了什么”的内容？

对应动作：

- `1` -> 更新 `README` / 页面说明 / 演示文档
- `2` -> 更新 `docs/api/openapi.yaml`
- `3` -> 更新架构文档，必要时补 ADR
- `4` -> 更新 `docs/runbooks/`
- `5` -> 补 ADR
- `6` -> 补 `docs/learning/`

## 6. 哪些文档优先级最高

### 第一优先级：必须尽量保持同步

- `README.md`
- `docs/api/openapi.yaml`
- `docs/architecture/README.md`
- `web/README.md`
- `docs/runbooks/` 中的联调/演示文档

这些文档一旦过期，最容易直接误导自己。

### 第二优先级：版本变化较大时同步

- `docs/product/scope.md`
- `docs/product/roadmap.md`
- `docs/releases/release-notes.md`

### 第三优先级：按需补充

- `docs/learning/`
- `deliverables/course/`

## 7. 如何避免文档变成累赘

### 7.1 不追求“一次写完所有文档”

工程文档不是一次成书，而是跟着功能迭代慢慢长出来。

### 7.2 不把所有实现细节都写进正式文档

正式文档只保留高价值事实。  
实现过程中的犹豫、试错和理解，放到 learning 或计划文档里。

### 7.3 允许存在“文档债”，但要显式

有时候你会来不及完全同步文档，这很正常。  
但要显式标记，而不是假装文档还完全正确。

可以使用的标记：

- `TODO: sync with implementation`
- `Draft`
- `Historical`
- `Outdated after V1.1`

最糟糕的情况不是“文档少”，而是“文档看起来很正式，但内容是假消息”。

## 8. 如何用 AI 协助文档管理

AI 最适合帮你做的是“提炼、归类、检查、生成最小草稿”，而不是替你写一堆没用的漂亮话。

### 8.1 功能开始前

可用 prompt：

```text
我要开始做一个新功能：XXX。
请帮我生成一份最小工程计划，包含：
- 目标
- 范围
- 不做什么
- 风险
- 验收标准
- 需要同步的文档
文档风格务实，不要空话。
```

### 8.2 实现偏航时

```text
我原计划做 XXX，但实现过程中发现：
- A
- B
- C

请帮我判断：
1. 哪些属于实现细节变化，可以不改正式文档
2. 哪些已经影响系统事实，必须同步文档
3. 应该更新哪些文档
```

### 8.3 功能完成后

```text
我刚完成了 XXX。
请根据下面的实现结果，帮我输出：
1. 应更新的 README 内容
2. 应更新的 API contract 内容
3. 是否需要 ADR
4. 一篇学习沉淀提纲
要求只写高信息密度内容，不要泛泛而谈。
```

### 8.4 面试沉淀

```text
我做完了 XXX。
请从面试准备角度，帮我整理：
- 这项工作的核心价值
- 为什么这样设计
- 关键取舍
- 常见追问
- 最佳回答思路
- 相关代码与文档入口
```

### 8.5 收口检查

```text
我准备结束这个迭代。
请帮我生成一份收口清单，检查：
- 哪些功能已经完成
- 哪些文档必须同步
- 哪些文档可以留到下一轮
- 是否存在文档与实现冲突
```

## 9. 针对 `my-AI` 的具体执行建议

在这个项目里，建议你以后固定遵守下面的节奏：

1. 做新功能前，在 `docs/runbooks/` 建一个小计划
2. 做关键架构取舍时，补 `docs/adr/`
3. 做完后至少检查：
   - `README.md`
   - `docs/api/openapi.yaml`
   - `docs/architecture/README.md`
   - `web/README.md`
4. 如果这一轮学到了一个关键技术点，补一篇 `docs/learning/`
5. 如果要准备课程展示，再从 `docs/` 整理到 `deliverables/course/`

推荐把每一轮开发都理解成“代码 + 正式文档 + 学习沉淀”的三件套，而不是只改代码。

## 10. 最终原则

如果以后只记住一件事，就记住下面这句话：

> 文档的目标不是完整，而是可信、可用、可持续。

对 `my-AI` 来说，最好的文档状态不是“很多”，而是：

- 你知道每份文档该放哪里
- 你知道什么时候该更新哪一类文档
- 文档不会和代码长期分家
- 文档能帮助你继续开发，也能帮助你把项目真正讲明白
