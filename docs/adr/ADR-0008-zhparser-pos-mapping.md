# ADR-0008：zhparser 中文分词词性映射策略

- 编号：ADR-0008
- 标题：zhparser 中文分词词性映射策略
- 状态：Accepted
- 日期：2026-06-21
- 修订：2026-06-22（V13：Java 查询预处理 + 完整词性映射）
- 接受日期：2026-06-21
- 相关 ADR：ADR-0003（V1 向量存储基线调整为 PGVector）
- 标签：qa, sparse-retrieval, zhparser, postgresql

## 背景

项目采用 PostgreSQL 16 + PGVector 作为统一存储，检索层同时支持三种模式：

- **Dense**：向量相似度检索（Spring AI PGVectorStore）
- **Sparse**：中文全文检索（PostgreSQL FTS + zhparser 扩展）
- **Hybrid**：RRF 融合 Dense + Sparse 结果

在评测阶段发现 Sparse 检索对所有查询返回空结果，导致 Hybrid 模式等同于 Dense-only，RRF 融合完全失效。

### 根因排查

1. **现象**：`SparseRetrievalAdapter` 的 `similaritySearch()` 始终返回空列表
2. **初步排查**：zhparser 扩展已安装、`content_tsv` 字段已生成、配置表 `zhparser.zhcfg` 存在
3. **深入定位**：V11 migration 中的 `zhparser.shcfg` 映射了过多词性到 simple 字典：
   - `v`（动词）→ 导致"是"、"有"、"能"等高频动词成为 tsquery 条件
   - `r`（代词）→ 导致"什么"、"怎么"、"哪个"、"到底"等疑问代词成为 tsquery 条件
4. **影响机制**：zhparser 默认生成 `AND` 逻辑的 tsquery，疑问代词作为必需条件与技术术语组合，但技术文档中几乎不包含这些口语化词汇，导致结果集为空

以查询"PGVector 到底怎么配置"为例：

```
-- V11 修复前（v/r 映射到 simple）：
-- tsquery: 'pgvector' & '到底' & '配置'
-- "到底" 在技术文档中不存在 → 结果为空

-- V11 修复后（v/r 不映射）：
-- tsquery: 'pgvector' & '配置'
-- 正常命中配置相关文档
```

## 备选方案

### 方案 A：保留全部词性（原方案）

- 描述：将 n/v/a/d/i/j/l/x/e/r 全部映射到 simple 字典
- 优点：分词最完整，理论上覆盖所有词汇
- 缺点：动词、代词产生的停用词（"是"、"什么"、"到底"）成为 tsquery 的必需 AND 条件，在技术文档检索场景下导致零结果

### 方案 B：去掉动词(v)和代词(r)，保留其余词性

- 描述：仅映射 n(名词)、a(形容词)、d(副词)、i(成语)、j(简称)、l(习语)、x(非语素)、e(叹词)
- 优点：去掉最高频的两类停用词来源，保留技术术语（名词）、属性描述（形容词）等核心语义
- 缺点：少量动词术语（如"部署"、"迁移"）可能被过滤，需通过自定义词典补充

### 方案 C：仅保留名词(n) + 自定义词典

- 描述：只映射名词，其余全部通过自定义词典手动补充
- 优点：最精准，完全避免噪声词
- 缺点：维护成本极高，每次新增文档域都需要扩充词典；丢失形容词、副词的检索信号

### 方案 D：Java 查询预处理 + 完整词性映射（V13 采用）

- 描述：数据库端保留最完整词性映射（n, v, a, d, i, j, l, x, e, m），仅排除 r(代词)；Java 端在 `SparseRetrievalAdapter.preprocessQuery()` 中用正则清除口语停用词
- 优点：数据库索引覆盖全部有价值词性（"配置"v、"优化"v、"近似"d、"最"d），查询端精准过滤噪声词
- 缺点：停用词表需要人工维护，正则匹配为字符级非词级，可能误伤复合词中的有效字符

## V11 → V12 → V13 评测演进

| 版本 | 词性映射 | Sparse HitRate (非CHITCHAT) | 变化原因 |
|------|----------|:---:|----------|
| V11 | n, a, d, i, j, l, x, e | **50.0%** (11/22) | 去 v 去 r，"粗暴降维"意外过滤了系动词噪声 |
| V12 | n, v, a, i, j, l, x, e, m | **22.7%** (5/22) | 加回 v 后"是""该"成为 AND 杀手；去掉 d 丢失"最""近似" |
| V13 | n, v, a, d, i, j, l, x, e, m | 待验证 | Java 预处理清除噪声词，数据库保留完整词性 |

**V12 暴跌根因分析**：

1. **v 中的"隐形毒瘤"**：zhparser 将"是"(系动词)、"该"(助动词) 标注为 v。V12 启用 v 后，查询 `plainto_tsquery('chinese', '我该怎么配置PGVector')` 变成 `'我' & '该' & '配置' & 'pgvector' & '数据库' & '环境'`，"该"在文档中不存在 → 一票否决
2. **d 中的"黄金特征"被误杀**："最"(d) 如"最近邻检索"、"近似"(d) 如"近似最近邻"，V12 去掉 d 后这些技术副词从索引中消失
3. **V11 的"因祸得福"**：去掉全部动词（v）无意中同时过滤了系动词，剩下的名词+英文在技术文档中密度极高，足以精准定位

## 决策

~~选择方案 B：去掉动词(v)和代词(r)，保留 n/a/d/i/j/l/x/e 8 类词性映射到 simple 字典。~~

**V13 修订**：选择方案 D —— Java 查询预处理 + 最完整词性映射。

- 数据库端：映射 `n, v, a, d, i, j, l, x, e, m`（仅排除 `r` 代词）
- Java 端：`SparseRetrievalAdapter.preprocessQuery()` 在查询送入 `plainto_tsquery` 前清除口语停用词

## 决策理由

1. **V12 的评测实证**：加回 v 后 Sparse HitRate 从 50% 暴跌至 22.7%，净失 6 条命中、0 新增，证明仅靠数据库端词性过滤无法平衡"保留技术动词"和"过滤口语噪声"
2. **查询预处理解耦索引与查询**：数据库端保留最完整词性（索引层做加法），Java 端清除停用词（查询层做减法），两层独立调优互不干扰
3. **RAG 架构标准做法**：工业级检索系统（Elasticsearch、Vespa、Weaviate）普遍采用查询预处理 + 完整索引的模式，而非在索引层粗粒度过滤
4. **保留技术动词的价值**："配置"、"优化"、"部署"、"迁移" 等动词在 PROCEDURAL 类查询中是核心信号，V11 丢弃 v 导致这类查询命中率偏低
5. **保留技术副词的价值**："最"(d) 如"最近邻检索"、"近似"(d) 如"近似最近邻"，V12 去掉 d 后丢失了这些 COMPARATIVE/ANALYTICAL 类查询的关键修饰词

## 影响

### 正向影响

- 数据库索引覆盖最完整词性，技术动词（"配置""优化"）和副词（"最""近似"）均可被检索
- 查询端停用词表可独立迭代，无需重建数据库索引或重新入库
- Hybrid 模式（RRF 融合）有望在 Sparse 贡献更多独立召回信号时进一步提升

### 负向影响 / 风险

- 需要重建所有中文文档的 `content_tsv` 向量列（Flyway V13 自动完成）
- 停用词正则为字符级匹配，可能误伤复合词中的有效字符（如 "是否" 中的 "是"）
- zhparser 的 POS 标注规则随版本变化，升级时需验证映射仍然正确

### 中立影响 / 权衡

- Java 预处理增加了约 0.1ms 的查询延迟（正则编译已通过 Pattern 静态常量缓存）
- 停用词表需要定期根据新查询模式补充
