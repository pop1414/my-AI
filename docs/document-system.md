# my-AI 文档体系

## 1. 目标

本文定义 `my-AI` 项目中主要文档类型的职责边界、生成顺序和 AI 协作角色。

这套体系的目标不是增加文档数量，而是让每份文档回答一个清晰问题：

- 为什么做
- 选什么方案
- 按什么节奏推进
- 具体如何落地
- 拆成哪些可执行任务
- 如何让后来者理解和使用

## 2. 文档类型总览

| 顺序 | 文档类型           | 核心关注点                                 | 关联逻辑         | AI 角色        |
| ---- | ------------------ | ------------------------------------------ | ---------------- | -------------- |
| 0    | Context / Glossary | 领域语言、核心实体、项目边界               | 统一项目语义     | 领域分析助手   |
| 1    | PRD                | 业务目标、用户问题、功能范围               | 定义项目的灵魂   | 产品经理助手   |
| 2    | ADR                | 技术选型、决策理由、取舍后果               | 确定项目的骨架   | 架构师助手     |
| 3    | Plan               | 阶段目标、里程碑、交付物、验收标准         | 规划项目的节奏   | 项目经理助手   |
| 4    | Spec (FS + TS)     | 功能逻辑、状态流、数据结构、接口、错误处理 | 绘制项目的施工图 | 资深开发助手   |
| 5    | Issue              | 具体开发任务、缺陷跟踪、可交付切片         | 拆成最小砖块     | 结对编程伙伴   |
| 6    | README             | 项目展示、运行方式、使用说明               | 生成项目的说明书 | 技术文档撰写员 |

## 3. 分层原则

这套文档体系不是严格的一次性流水线，而是分层决策体系。

```text
Context / Glossary -> 统一语言
PRD                -> 决定做什么、为什么做
ADR                -> 记录关键技术决策为什么这样选
Plan               -> 决定按什么阶段推进
Spec               -> 决定具体逻辑如何落地
Issue              -> 决定每个最小可交付任务怎么执行
README             -> 说明别人如何理解、运行和使用项目

```

其中 `ADR` 不是固定只在 `PRD` 后、`Plan` 前产生。任何阶段只要出现影响未来演进的关键技术取舍，都应补充或更新 ADR。

## 4. 各文档职责

### 4.1 Context / Glossary

回答的问题：

- 当前项目的长期业务语义是什么
- 核心实体叫什么
- 哪些术语不能混用
- 当前系统边界在哪里

在本仓库中的主要入口：

- `CONTEXT.md`
- `docs/agents/domain.md`

使用规则：

- 写 PRD、Spec、Issue 前，应优先读取领域上下文
- 不要为已有概念发明新的同义词
- 如果新增稳定领域概念，应同步更新上下文或相关领域文档

### 4.2 PRD

回答的问题：

- 用户面对什么问题
- 这次要解决什么
- 功能范围是什么
- 哪些明确不做
- 用户完成后获得什么价值

PRD 应重点描述业务目标和用户视角，不应提前塞入过多实现细节。

推荐包含：

- Problem Statement
- Solution
- User Stories
- Implementation Decisions
- Testing Decisions
- Out of Scope
- Further Notes

### 4.3 ADR

回答的问题：

- 为什么选择这个技术方案
- 替代方案是什么
- 当前决策带来什么约束
- 未来维护者需要知道哪些代价

在本仓库中的位置：

- `docs/adr/`

适合写 ADR 的情况：

- 引入新的基础设施
- 改变模块边界
- 改变数据归属或状态语义
- 改变安全、权限、存储、解析、调度等长期策略

不适合写 ADR 的情况：

- 局部 helper 拆分
- 小型代码重构
- 临时实现细节

### 4.4 Plan

回答的问题：

- 分几个阶段做
- 每个阶段交付什么
- 阶段完成标准是什么
- 当前有哪些风险和依赖

Plan 不应只写时间点。对本仓库来说，更稳定的 Plan 结构是：

- 阶段目标
- 交付物
- 验收标准
- 风险
- 依赖
- 文档同步点

推荐位置：

- `docs/runbooks/plans/`

### 4.5 Spec (FS + TS)

回答的问题：

- 用户动作触发什么系统行为
- 状态如何流转
- 数据结构如何定义
- API contract 是什么
- 异常和边界条件如何处理
- 需要哪些测试保护行为

其中：

- `FS` 表示 Functional Specification，描述功能规则和用户可见行为
- `TS` 表示 Technical Specification，描述技术结构、接口、状态、错误和测试策略

Spec 是从 PRD 到代码实现之间最重要的施工图。它应比 PRD 更具体，但应避免绑定到具体的文件路径或临时代码片段。

### 4.6 Issue

回答的问题：

- 当前最小可交付任务是什么
- 谁可以领取
- 完成后如何验收
- 是否被其他任务阻塞

Issue 应优先按 vertical slice 拆分，而不是按数据库、后端、前端、测试做 horizontal slice。

好的 Issue 应具备：

- 一条窄但完整的端到端路径
- 明确的 acceptance criteria
- 清晰的 blocked by 关系
- 可独立验证的完成状态

推荐标签：

- 可交给 agent 独立完成：`ready-for-agent`
- 需要人类决策或验收：`ready-for-human`
- 信息不足：`needs-info`

### 4.7 README

回答的问题：

- 这个项目是什么
- 当前能做什么
- 如何运行
- 如何验证
- 主要文档入口在哪里

README 不是内部实施日志。它应面向后来者，提供稳定入口和最小必要说明。

README 分两类：

- 根目录 `README.md`：项目总入口
- 子目录 README：局部模块或目录说明

## 5. 推荐协作流程

### 5.1 新功能从零开始

推荐顺序：

1. 先更新或确认 Context / Glossary
2. 写 PRD，明确业务目标和范围
3. 遇到关键技术取舍时写 ADR
4. 写 Plan，拆阶段与验收标准
5. 写 Spec，明确功能规则和技术契约
6. 用 Issue 拆成可执行 vertical slices
7. 功能完成后更新 README 和相关核心文档（如 Spec、ADR 等）

### 5.2 已有功能增强

推荐顺序：

1. 读取 Context、相关 ADR、现有 Plan / Spec
2. 判断当前增强是否改变业务范围
3. 如果改变业务目标，补 PRD
4. 如果改变关键技术取舍，补 ADR
5. 如果只是执行路径变化，更新 Plan / Spec / Issue
6. 完成后同步 README、API contract、架构或 runbook

### 5.3 Bug 修复

推荐顺序：

1. Issue 描述问题、复现路径和验收标准
2. 如果暴露出设计缺陷，补 Spec 或 ADR
3. 如果改变用户可见行为，更新 README 或相关使用说明
4. 如果形成排障经验，补 runbook 或 learning 文档

## 6. 以文档解析与清洗优化为例

假设目标是优化文档解析与清洗，通过 HTTP 调用 Docling 服务，并引入 MinIO（或 S3‑compatible 存储）。

对应文档流转可以是：

1. `Context / Glossary`：明确 `document`、`document version`、`cleaned.md`、`S3-compatible document asset storage`、`Docling Service` 等术语边界。
2. `PRD`：说明为什么要增强文档解析质量、为什么需要可追踪的处理状态、用户从中获得什么价值。
3. `ADR`：记录为什么通过 HTTP 调用 Docling，为什么使用 MinIO 或其他 S3-compatible storage 保存源文件和处理产物。
4. `Plan`：拆成存储接入、解析服务集成、清洗链路、状态与重试、验收回归几个阶段。
5. `Spec`：定义状态流转、HTTP contract、对象 key 规则、错误映射、清洗规则和测试策略。
6. `Issue`：拆成可独立完成的 vertical slices，例如“上传后保存源文件并形成版本记录”“调用 Docling 生成解析结果”“清洗结果落成 cleaned.md”“支持失败重试与状态查询”。
7. `README`：功能稳定后更新运行依赖、配置示例和文档处理流程说明。

## 7. 目录落位规则

当前 `docs/` 采用“顶层导航 + 职责子目录”的结构。顶层只保留跨目录入口和文档治理说明，具体主题文档必须进入对应子目录，避免长期演进后再次堆成平铺列表。

```text
docs/
  README.md                 # 文档导航、推荐阅读顺序、目录职责摘要
  document-system.md        # 文档体系、文档类型、目录落位规则

  product/                  # 产品范围、路线图、阶段目标
  architecture/             # 架构总览、子域设计、图纸资产
  api/                      # OpenAPI 等接口契约
  releases/                 # 发布说明、版本变化记录
  adr/                      # 架构决策记录
  runbooks/                 # 执行计划、联调手册、演示脚本、排障手册
  learning/                 # 学习沉淀、复盘、面试表达
  reference/                # 外部参考资料、技术对照材料
  agents/                   # Agent 协作约定和 issue tracker 说明
  archive/                  # 已归档但仍需保留的历史材料
```

### 7.1 顶层文件规则

`docs/` 顶层只允许放：

- `README.md`：告诉读者从哪里开始看，以及各目录负责什么。
- `document-system.md`：定义文档类型、生成顺序、目录落位和 AI 协作方式。
- 极少数跨目录治理文件：必须能解释为什么不能归入某个主题目录。

除上述情况外，新增文档不应直接放在 `docs/` 顶层。

### 7.2 子目录职责

- `docs/product/`：放产品范围、路线图、版本目标、长期边界。它回答“做什么、当前做到哪、未来往哪里走”。
- `docs/architecture/`：放当前系统结构、模块边界、核心链路、子域设计和图纸索引。它回答“系统现在怎么组织、关键关系是什么”。
- `docs/api/`：放对外接口契约，例如 OpenAPI。它回答“前后端和外部调用方按什么协议协作”。
- `docs/releases/`：放发布说明和版本变化记录。它回答“每个版本新增、变更、修复了什么”。
- `docs/adr/`：放长期有效的技术决策。它回答“为什么选这个方案，以及这个选择带来什么约束”。
- `docs/runbooks/`：放执行型材料，包括计划、联调、演示、排障和交接。它回答“具体怎么推进、怎么验证、怎么恢复”。
- `docs/learning/`：放学习笔记、踩坑复盘和面试表达。它可以有主观总结，但不能替代工程事实真源。
- `docs/reference/`：放外部资料和技术参考。它只作为输入材料，不直接代表当前系统事实。
- `docs/agents/`：放 Agent 协作所需的 issue tracker、triage label 和领域文档入口说明。
- `docs/archive/`：放已完成、已废弃或不再作为当前入口的历史资料。

### 7.3 新增文档判断顺序

新增文档前按以下顺序判断位置：

1. 是否是长期产品边界或路线？是则放 `docs/product/`。
2. 是否描述当前架构、状态机、领域关系或模块职责？是则放 `docs/architecture/`。
3. 是否是接口契约？是则放 `docs/api/`。
4. 是否是版本变化记录？是则放 `docs/releases/`。
5. 是否记录关键技术取舍？是则放 `docs/adr/`。
6. 是否是执行计划、演示、联调、排障或交接？是则放 `docs/runbooks/`。
7. 是否是学习复盘或表达材料？是则放 `docs/learning/`。
8. 是否只是外部参考？是则放 `docs/reference/`。

如果一个文档同时命中多个目录，优先按它的“主要读者和主要用途”归位；必要时在另一个目录放链接，不复制第二份正文。

### 7.4 移动和重命名规则

移动文档时必须同步处理：

- 更新 `docs/README.md` 的推荐阅读顺序和目录职责。
- 更新根目录 `README.md`、`CONTEXT.md`、runbook、learning 笔记中的旧路径引用。
- 如果移动的是接口契约或架构总览，检查代码注释中是否引用了旧路径。
- 全仓搜索旧文件名，确保没有残留引用。
- 不保留同内容副本；历史路径只通过 Git 追踪。

## 8. 写作边界

### 8.1 避免重复记录

同一事实只应有一个权威位置。

- 当前系统事实放 `docs/` 主文档
- 技术取舍放 `docs/adr/`
- 执行计划放 `docs/runbooks/plans/`
- 操作步骤和排障放 `docs/runbooks/`
- 学习复盘放 `docs/learning/`

### 8.2 区分当前事实、决策和计划

写文档时应明确区分：

- 当前已经实现的事实
- 已经采纳但尚未完全落地的决策
- 未来计划
- 暂时不做的范围

### 8.3 Issue 不替代 Spec

Issue 是执行砖块，不是完整设计文档。复杂逻辑、状态机、接口契约和错误处理应先进入 Spec，再拆成 Issue。

### 8.4 README 不替代工程真源

README 负责入口和使用说明，不承载全部设计细节。详细设计应链接到对应 PRD、ADR、Spec 或 runbook。

## 9. AI 协作方式

不同文档类型对应不同 AI 角色：

- 写 PRD 时，AI 应扮演产品经理助手，聚焦问题、用户价值和范围边界
- 写 ADR 时，AI 应扮演架构师助手，聚焦选型、取舍和长期后果
- 写 Plan 时，AI 应扮演项目经理助手，聚焦阶段、依赖、风险和验收
- 写 Spec 时，AI 应扮演资深开发助手，聚焦逻辑、接口、状态和测试
- 写 Issue 时，AI 应扮演结对编程伙伴，聚焦最小可交付切片和验收条件
- 写 README 时，AI 应扮演技术文档撰写员，聚焦入口、运行、使用和验证

使用 AI 生成文档时，应优先要求它引用已有上下文和 ADR，不要脱离仓库的实际状况自由发挥。
