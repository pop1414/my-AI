# AI-Native 文档系统

> 面向 AI 辅助开发时代的通用文档体系规范。
>
> 目标读者是人类开发者和 AI 编码助手。它的目标不是增加文档数量，而是让 AI 在开始工作前能读到稳定、分层、可验证的项目上下文。

---

## 1. 核心理念

### 1.1 文档的第一读者是 AI

AI 没有跨会话记忆。每次新会话开始时，它都需要重新理解项目的领域语言、技术决策、功能规格和当前任务。

因此，文档不只是写给未来的人，也是在给 AI 提供可复用上下文。写文档时优先问：

> AI 能否从这份文档中准确理解我的意图、边界和验证方式？

### 1.2 控制点从代码前移到 Spec

在手工编码时代，人的控制力主要体现在代码上。AI 编码时代，人的控制力必须前移到规格说明。

```text
手工编码时代：人 -> 代码 -> 测试 -> 交付
AI 编码时代： 人 -> Spec -> AI 生成代码 -> 验证 Spec -> 交付
```

Spec 的职责是定义“什么是正确的”。AI 可以负责实现，但人必须掌控正确性的定义。

### 1.3 文档是分层决策，不是瀑布流程

AI-native 文档体系不是要求每个项目都按固定顺序产出所有文档，而是把不同层级的决策放到合适的位置。

```text
CONTEXT.md         -> 稳定领域语言、核心实体、项目边界
PRD.md             -> 做什么、为什么做、哪些不做
ADR                -> 长期技术取舍及后果
PLAN.md            -> 阶段、顺序、依赖、风险
SPEC.md            -> 功能契约、技术契约、验证命令
issues/            -> 最小可交付任务切片
```

这些文档之间是引用和细化关系，不是线性流水线。一个 Spec 可能反过来要求更新 Context；一个 Bug 修复可能催生 ADR；一个 Issue 的执行结果也可能暴露出文档腐化。

### 1.4 可执行验证是约束力来源

只写意图无法约束 AI。真正有效的是“文档 + 可执行验证命令”。

```text
弱约束：需要测试用户注册功能
强约束：运行 npm test -- user-registration.spec.ts，预期全部通过
```

每个 Spec 和可执行 Issue 都应包含 AI 可以直接运行或明确复述的验证方式。

### 1.5 文档服务开发

- 每份文档只回答一个层级的问题。
- 不需要的文档层可以跳过。
- 文档的价值来自实际使用，不来自形式完整。
- 如果文档没有被人或 AI 使用，应删除、合并或改写。

## 2. 文档类型与生成入口

具体文档格式由负责生成该文档的 producer skill 维护。框架层只规定路径、职责和流转边界。

| 类型    | 核心问题                                      | 推荐位置                                           | 何时创建                 | Producer skill    | 格式来源                                   |
| ------- | --------------------------------------------- | -------------------------------------------------- | ------------------------ | ----------------- | ------------------------------------------ |
| Context | 项目的稳定领域语言、核心实体、边界            | `CONTEXT.md`                                       | 项目开始或领域语言混乱时 | `grill-with-docs` | `skills/grill-with-docs/CONTEXT-FORMAT.md` |
| ADR     | 技术取舍、替代方案、后果                      | `docs/adr/<NNNN>-<slug>.md`                        | 出现长期技术决策时       | `grill-with-docs` | `skills/grill-with-docs/ADR-FORMAT.md`     |
| PRD     | 用户问题、目标、范围、非目标                  | `docs/features/<feature>/PRD.md`                   | 新功能启动时             | `to-prd`          | `skills/to-prd/SKILL.md`                   |
| Plan    | 阶段、顺序、依赖、风险                        | `docs/plans/` 或 `docs/features/<feature>/PLAN.md` | 工作跨阶段或依赖复杂时   | `to-plan`         | `skills/to-plan/SKILL.md`                  |
| Spec    | 行为契约、技术契约、异常路径、验证命令        | `docs/features/<feature>/SPEC.md`                  | AI 独立实现前            | `to-spec`         | `skills/to-spec/SKILL.md`                  |
| Issue   | 最小可交付 vertical slice、验收标准、验收命令 | `docs/features/<feature>/issues/`                  | 准备执行时               | `to-issues`       | `skills/to-issues/SKILL.md`                |

## 3. 文档职责边界

本节定义每类文档承载什么决策、不承载什么内容。这是框架层规则，独立于具体由哪个 skill 生成。

### 3.1 Context

Context 是长期真相源，记录项目稳定的领域语言和边界。

应包含：

- 项目目标和边界
- 核心实体定义
- 领域术语表
- 禁止混用的同义词
- 明确不做的范围

不应包含：

- API contract
- 数据库 schema
- 功能清单
- 临时任务状态

### 3.2 PRD

PRD 负责定义产品意图。

应包含：

- 用户问题
- 解决方案概述
- 用户故事
- 功能范围
- 非目标
- 业务验收标准

不应包含：

- API 签名
- 数据库表结构
- 内部类名或文件路径
- 具体实现步骤

### 3.3 ADR

ADR 记录有长期影响的技术取舍。

适合写 ADR 的情况：

- 引入新的基础设施
- 改变模块边界
- 改变数据归属或状态语义
- 改变安全、权限、存储、解析、调度策略
- 两种以上可行技术方案需要取舍

不适合写 ADR 的情况：

- 局部 helper 函数拆分
- 不改变外部行为的小重构
- 临时实现细节
- 个人编码风格偏好

ADR 是事件驱动的。不是每个 PRD 后面都必须有 ADR，而是只在真实取舍出现时记录。

### 3.4 Plan

Plan 负责组织阶段和顺序。

应包含：

- 阶段目标
- 交付物
- 完成标准
- 依赖关系
- 风险和缓解措施
- 文档同步点

如果一个功能只需要一个 Spec 加少量 Issue 就能描述清楚，可以跳过 Plan。

### 3.5 Spec

Spec 是 AI 编码前最重要的控制点。它定义行为契约和技术契约。

应包含：

- 用户场景
- 状态流转
- 业务规则
- 错误场景
- 数据模型
- API contract
- 验证规则
- 自动化验证命令
- 必要的手工 QA 步骤

Spec 描述契约，不描述具体实现。它应足够具体，让 AI 能独立实现；也应保留合理实现空间，避免把文档写成伪代码。

### 3.6 Issue

Issue 是执行的最小单元，通常从 Spec 拆分而来。

一个好的 Issue 应该：

- 能在 1-2 个 AI 会话内完成
- 完成后能独立验收
- 有清晰范围和非范围
- 有明确验收标准
- 有可执行或可复述的验证方式
- 说明阻塞关系

Issue 应按 vertical slice 拆分，优先交付一条可观察的端到端路径，而不是按技术层横向拆分。

## 4. 推荐文档链

### 4.1 新功能

```text
读取 Context
  -> 编写或更新 PRD
  -> 如有长期技术取舍，创建 ADR
  -> 如需阶段规划，创建 Plan
  -> 编写 Spec，明确验证命令
  -> 拆分 Issue
  -> AI 执行 Issue
  -> 运行验证
  -> 同步相关项目文档
```

### 4.2 已有功能增强

```text
读取当前工具入口和相关项目文档
  -> 判断是否改变产品范围
  -> 必要时更新 PRD
  -> 判断是否引入技术取舍
  -> 必要时创建 ADR
  -> 更新 Spec 和验证命令
  -> 拆分或更新 Issue
  -> 执行并验证
```

### 4.3 Bug 修复

```text
读取相关 Spec
  -> 创建或更新 Issue，写清复现路径
  -> 判断是否暴露设计缺陷
  -> 必要时更新 Spec 或 ADR
  -> 修复并运行验证
  -> 必要时同步 runbook 或学习记录
```

## 5. 追溯关系

每个文档应能追溯到上游意图。

最低要求：

- Spec 注明关联的 PRD
- Issue 注明关联的 Spec
- ADR 注明触发它的 PRD、Spec、Bug 或讨论
- 具体 AI 工具入口文件按需指向这套文档链

推荐在文档头部使用轻量引用：

```markdown
<!--
Related:
  - Context: CONTEXT.md
  - Parent PRD: docs/features/example/PRD.md
  - Parent Spec: docs/features/example/SPEC.md
  - ADR: docs/adr/0001-example.md
-->
```

## 6. 文档腐化防御

### 6.1 更新触发

当出现以下情况时，应同步更新文档：

- 代码行为和 Spec 不一致
- 新增稳定领域概念
- 功能范围变化
- 验证命令失效
- 技术决策被替代
- Issue 执行连续偏离上游 Spec

### 6.2 审查节奏

| 文档    | 建议审查时机                     |
| ------- | -------------------------------- |
| Context | 每个重要功能完成后               |
| PRD     | 功能范围变化或功能完成归档时     |
| ADR     | 不主动改写历史，只在被替代时标记 |
| Plan    | 每个阶段结束时                   |
| Spec    | 发布前或行为变化后               |
| Issue   | 执行过程中持续更新               |

### 6.3 AI 行为约束

AI 在开始任务时应检查：

- 当前任务需要读取哪些文档
- 术语是否与 Context 一致
- 相关 ADR 是否仍约束当前实现
- Spec 是否包含足够验证方式
- Issue 是否可以独立执行和验收

如果发现不一致，应显式标记 `[文档可能过时]`，不要静默忽略。

## 7. 裁剪规则

并非所有项目都需要完整文档链。

| 场景         | 必留                            | 可选           |
| ------------ | ------------------------------- | -------------- |
| 一次性脚本   | 运行说明                        | Context        |
| 小型功能     | Context, Spec, Issue            | PRD, ADR       |
| 普通产品功能 | Context, PRD, Spec, Issue       | ADR, Plan      |
| 跨阶段工作   | Context, PRD, Plan, Spec, Issue | ADR            |
| 长期系统     | 全部文档层                      | 路径级补充说明 |

裁剪原则：

- 没有真实取舍，不写 ADR。
- 没有阶段协调，不写 Plan。
- 功能足够清楚时，PRD 可以很短。
- AI 要独立实现前，Spec 和验证命令不能省。
- 具体输出格式由对应 producer skill 决定，职责边界不要混用。

---

## 8. 可选 BMad 扩展

AI-native 文档系统本身不依赖 BMad。需要更强复杂性展开、readiness、story cycle 或 review gate 时，可以启用 BMad 扩展。

- 融合规则见 `BMAD_INTEGRATION.md`。
- Level 3 节点流程见 `LEVEL3_BMAD_WORKFLOW.md`。

BMad 输出不是正式真相源。它提出、拆解、审计和记录执行；正式约束必须晋升到 `docs/` 中对应的 AI-native 文档后才生效。
