# 并行开发边界约定：权限治理与文档处理优化

日期：2026-05-09  
适用分支：

- `feature/auth-authorization-governance`
- `feature/ingest-cleaning-optimization`

## 1. 目的

为避免权限治理与文档处理优化两条工作流在并行开发时互相踩踏，
需要提前约定模块边界、禁止改动范围、升级触发条件和合并注意事项。

本约定的目标不是阻止协作，而是降低以下风险：

- 同一阶段多分支反复改同一批文件
- 一条线引入 schema 或契约变化，另一条线毫不知情
- 问题排查时无法判断行为变化来自权限逻辑还是文档处理逻辑

## 2. 分支职责

### 2.1 权限治理分支职责

`feature/auth-authorization-governance` 只负责：

- 工作区成员管理
- 知识库授权管理
- 文档授权管理
- 审计事件查询
- 上述治理动作的审计写入和回归测试

### 2.2 文档处理优化分支职责

`feature/ingest-cleaning-optimization` 只负责：

- 文档解析质量优化
- 文本清洗规则优化
- 现有 chunker 的兼容性优化
- 中间产物与轻量解析元数据设计
- 与 ingest 质量有关的回归测试

补充约束：

- 允许为 `cleaned.md` 主链和 `Path/Reader` 边界改造现有 chunker
- 不引入新的节点模型
- 不引入新的分块策略

## 3. 默认禁止改动范围

### 3.1 权限治理分支禁止内容

- 不修改 `TikaDocumentTextParser`
- 不修改 `TextCleaningService`
- 不修改 `StructuredFallbackDocumentChunker`
- 不修改 `ProcessDocumentApplicationService` 的解析 / 分块主流程
- 不顺手调整文档中间产物存储方案

### 3.2 文档处理优化分支禁止内容

- 不修改成员管理接口
- 不修改知识库授权管理接口
- 不修改文档授权管理接口
- 不修改审计查询接口
- 不修改工作区成员、知识库授权、文档授权的治理规则

## 4. 允许交叉但需显式同步的内容

以下内容不是绝对禁止，但一旦发生，必须先同步：

1. Flyway 迁移
2. `docs/04-api-contract.yaml` 的接口契约变更
3. `documents/chunks/preview` 返回结构变更
4. `qa.ask` 引用片段来源结构变更
5. 文档处理中间产物从内存字符串切换为文件化 / `Path` / `Reader` 主链
6. `ingest_documents.processing_metadata` 字段新增或结构升级

同步要求：

- 先在对应 runbook 文档中写清变化范围
- 再决定是否要让另一条分支临时 rebase 或延后合并

## 5. 建议文件所有权

### 5.1 权限治理分支优先所有权

- `src/main/java/io/github/spike/myai/auth/**`
- `src/main/java/io/github/spike/myai/knowledge/**` 中的治理型接口与应用服务
- 后续新增的成员 / 授权 / 审计控制器与用例
- `docs/04-api-contract.yaml` 中治理接口部分

### 5.2 文档处理优化分支优先所有权

- `src/main/java/io/github/spike/myai/ingest/infrastructure/parser/**`
- `src/main/java/io/github/spike/myai/ingest/infrastructure/chunking/**`
- `src/main/java/io/github/spike/myai/ingest/application/service/ProcessDocumentApplicationService.java`
- `src/test/java/io/github/spike/myai/ingest/**`
- `docs/runbooks/plans/ingest-cleaning/**`

### 5.3 共享文件

以下文件属于共享文件，改动前应先判断是否影响另一条线：

- `src/main/java/io/github/spike/myai/qa/application/service/AskQuestionApplicationService.java`
- `src/main/java/io/github/spike/myai/ingest/interfaces/rest/DocumentIngestController.java`
- `docs/04-api-contract.yaml`

## 6. 合并顺序建议

### 6.1 可独立合并的情况

若文档处理优化只涉及算法、清洗规则和现有分块器优化，
且不引入 schema 变化或对外契约变更，则两条分支可独立合并。

### 6.2 应优先合并文档处理分支的情况

若文档处理优化涉及以下内容，建议优先合并 `feature/ingest-cleaning-optimization`：

- 新增或修改 Flyway 迁移
- 新增文档解析元数据字段
- 修改 `documents/chunks/preview` 输出结构
- 调整 `qa.ask` 所依赖的分块数据来源

### 6.3 应优先合并权限治理分支的情况

若文档处理优化不触及 schema 和接口契约，而治理接口已经形成稳定后端边界，
则可先合并 `feature/auth-authorization-governance`，降低后台接口长期悬挂风险。

## 7. 冲突处理原则

出现冲突时按以下原则处理：

1. 先判断冲突属于“同一文件不同职责”还是“真实设计冲突”
2. 如果只是共享文件上的局部改动，优先保留各自职责边界内的实现
3. 如果涉及 schema、状态机或接口契约，暂停合并，先回写文档再继续
4. 不允许在未同步文档的情况下临时修改另一条线的核心设计

## 8. 一句话原则

**权限治理分支负责“谁能管”，文档处理优化分支负责“文档内容长什么样”；凡是会同时改变“权限结果”和“内容形态”的改动，必须先同步再实施。**
