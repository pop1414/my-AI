# 文档详情页版本历史交互确认

## 1. 文档目标

本文用于确认 GitHub issue #2《文档详情页版本历史交互确认》的前端交互方案。

目标不是直接实现页面，而是把后续前端开发所需的交互边界一次定清楚，尤其是：

- 版本历史列表默认展示什么
- 历史版本查看态如何与最新版本主视图区分
- 顶部差异摘要区如何比较、放在哪里
- 上传新版本与版本回退后的稳定结果提示区如何组织
- “返回最新版本”如何工作

本文严格遵循 `CONTEXT.md` 中的领域约束：

- 详情页主视图默认锚定 `document` 当前最新版本
- 历史版本查看仅用于审计/治理查看，不改变系统当前最新版本与问答基线
- 版本历史仅对具备目标 `document` 管理权限的用户可见
- 问答基线按 `askable version` 运行时推导，不等同于当前查看版本

## 2. 设计方向

沿用当前 `web` 控制台 + Ant Design 的整体语言，不另起一套品牌风格；但在文档详情页里引入更强的“版本账本”气质。

页面视觉方向定为：

- 左侧是“当前查看版本的事实面板”，强调这次到底在看哪个版本
- 右侧是“版本账本时间轴”，强调同一 `document` 的线性演进
- 顶部用清晰的状态条和差异摘要，把“最新版本事实”和“当前问答基线事实”拆开说清

这意味着页面不追求花哨，而追求三件事：

- 一眼看清当前正在看哪个版本
- 一眼看清系统认定的最新版本和当前可问答版本是否一致
- 一眼看清从哪个历史版本可以做什么治理动作

## 3. 页面信息架构

### 3.1 Desktop

```text
页面头部
稳定结果提示区（仅在上传新版本 / 回退后显示）
历史查看提示条（仅在查看历史版本时显示）
差异摘要区

左 8 列
- 当前查看版本概览卡
- 文档详情卡
- 处理/问答上下文卡

右 4 列
- 版本历史账本卡（sticky）
```

### 3.2 Mobile

```text
页面头部
稳定结果提示区
历史查看提示条
差异摘要区
当前查看版本概览卡
文档详情卡
处理/问答上下文卡
版本历史账本卡（默认折叠）
```

### 3.3 路由建议

- 详情页主路由建议收敛为：`/ingest/documents/:documentId`
- 查看历史版本使用 query：`?version=4`
- 查看某个版本的正文内容使用独立子路由：`/ingest/documents/:documentId/versions/:versionNumber/read`
- “返回最新版本”本质上是移除 `version` query，回到无 query 的最新版本视图

如果实现阶段暂时保留当前 `/ingest/documents/:documentId/status` 路由，可先将其作为兼容入口，再重定向到新详情路由。

## 4. 版本历史列表确认

## 4.1 排序规则

- 按 `versionNumber` 倒序排列，最新版本始终在最上方
- 不按更新时间重新排序，避免破坏版本链线性认知

## 4.2 默认展示字段

每个版本列表项默认展示以下信息：

- `v{versionNumber}` 版本号
- 版本来源标签：`上传产生` / `回退产生`
- 来源文件名 `filename`
- 更新时间 `updatedAt`
- 上传人/创建人显示名
- 当前处理状态 `status`
- 当前是否为问答基线：`当前问答基线`
- 当版本由回退产生时，显示“回退自 vN”
- 当该历史版本曾被回退为最新版本时，显示“曾回退为最新版本”

不放入默认列表项的字段：

- `fileHash`
- 原始错误长文本
- `processingMetadata` 全量 JSON
- 文本分块预览

这些内容属于详情区或后续扩展信息，不应污染版本账本扫描效率。

## 4.3 标记体系与顺序

同一列表项的标签顺序固定为：

1. `最新版本`
2. `当前查看`
3. `当前问答基线`
4. `回退产生`
5. `曾回退为最新版本`
6. 状态标签：`UPLOADED` / `INGESTING` / `INDEXED` / `FAILED` / `DELETING` / `DELETED`

说明：

- `最新版本` 是系统事实，优先级最高
- `当前查看` 是用户视角，必须和 `最新版本` 分开
- `当前问答基线` 用于显式拆开“治理主视图”与“问答实际使用版本”
- 状态标签永远放最后，避免和业务语义标签抢层级

## 4.4 折叠规则

- 默认展开最近 `5` 个版本
- 若版本总数超过 `5` 个，剩余旧版本折叠到“展开更早版本（N）”
- 当前查看版本、最新版本、当前问答基线版本必须始终可见
- 如果上述特殊版本落在折叠区内，需要自动把它提升到可见区，而不是要求用户先展开

这套规则的目的是：

- 新链路下用户大多数时候只关心最近几次演进
- 但不能把“当前问答基线仍停留在旧版本”这样的关键事实藏起来

## 4.5 列表项动作

每个版本项的默认动作如下：

- `查看详情`
- `查看该版本内容`
- `回退为最新版本`，仅当该版本满足回退条件且当前用户具备管理权限时显示

动作显隐规则：

- 最新版本不显示 `回退为最新版本`
- 非 `INDEXED` 历史版本不显示 `回退为最新版本`
- 没有管理权限时，不展示旧版本列表，也不展示任何版本治理动作

## 5. 历史版本查看态确认

## 5.1 进入方式

- 点击版本历史列表项的 `查看详情`
- 从稳定结果提示区点击“查看版本历史”后，默认滚动到账本区并高亮相关版本

## 5.2 页面区分方式

进入历史版本查看态后，页面必须同时发生三类变化：

- 顶部出现历史查看提示条
- 主概览卡从“最新版本概览”切换为“历史版本概览”
- 页内主按钮从“治理当前最新版本”切换为“返回最新版本 / 回退为最新版本”

历史查看提示条文案建议：

- 标题：`正在查看历史版本 vN`
- 说明：`此视图仅用于审计与治理查看，不会改变当前最新版本与问答基线`

## 5.3 历史查看态下保留与收起的动作

历史查看态下：

- 保留 `返回最新版本`
- 保留 `回退为最新版本`，前提是该历史版本满足条件
- 隐藏 `上传新版本`
- 隐藏基于“当前查看版本”误导用户的 `重处理`、`删除 document` 主按钮

原因很直接：

- `上传新版本` 只能基于当前最新版本发起
- `删除 document` 是面向整个 `document` 资产的治理动作，不应跟着历史版本视图漂移
- `重处理` 当前阶段仍是最新版本治理动作，不应让用户误以为可以对任意历史版本单独重处理

## 5.4 返回最新版本

“返回最新版本”行为定义为：

- 清除 `version` query
- 主视图切回当前最新版本
- 版本历史列表高亮最新版本项
- 差异摘要区切换为“最新版本 vs 上一版本”
- 保留当前页内滚动位置，避免频繁跳页

如果用户是从稳定结果提示区进入历史查看，再点击“返回最新版本”，稳定结果提示区继续保留，不自动消失。

## 5.5 查看该版本内容

当用户的目标从“做版本治理决策”切换为“阅读某个版本正文”时，应离开当前详情页，进入独立的版本内容阅读页，而不是在治理页内继续下钻。

原因：

- 正文阅读与版本治理属于两种不同任务，不应争抢同一主视图
- 正文通常很长，继续留在治理页会压缩版本账本、差异摘要和治理动作的可读性
- 独立阅读页更适合承接后续的下载、正文预览、引用定位和分块预览入口

阅读页应遵循以下规则：

- 顶部明确显示 `documentId`、`versionNumber`、当前是否为最新版本、当前问答基线版本
- 页面内提供 `返回版本详情` 动作，回到原治理页的当前查看上下文
- 阅读页只负责看“这版内容长什么样”，不在正文区域承载上传新版本、回退、删除等治理动作
- 进入阅读页不会改变当前最新版本、当前问答基线，也不会改变治理页的当前查看版本
- 阅读页应支持“单栏阅读”和“并排对照阅读”两种模式；并排模式允许用户选择两个版本，在同一大界面中左右对照查看

## 6. 顶部差异摘要区确认

## 6.1 位置

差异摘要区固定放在：

- 稳定结果提示区下方
- 历史查看提示条下方
- 当前查看版本概览卡上方

这样它始终处于“我现在看的是谁”与“它和谁不同”之间。

## 6.2 默认比较对象

分两种情况：

- 最新版本主视图：`当前最新版本` vs `上一版本`
- 历史版本查看态：`当前查看版本` vs `当前最新版本`

这条规则不要改成“历史版本 vs 它自己的前一版本”，原因是 issue #2 的核心决策场景是：

- 我现在看这个旧版本，和当前生产态相比差在哪里
- 我要不要把它回退为新的最新版本

## 6.3 摘要粒度

当前阶段差异摘要只做“结构化元数据差异”，不做正文 diff。

默认展示 4 块摘要：

1. 版本关系
   `v4` 与 `v7` 的关系；若当前查看版本曾被回退过，也在这里说明
2. 文件变化
   文件名是否变化、文件大小是否变化
3. 处理与问答状态
   两个版本各自的 `status`，以及哪个版本是当前 `askable version`
4. 时间与来源
   版本来源类型、更新时间差、是否为回退产生

如果后续 `processingMetadata` 中沉淀出稳定、可读的结构化摘要，可以在差异区追加“解析结果摘要”，但不作为本 issue 的前置依赖。

## 6.4 空态规则

- 当 `document` 只有 `v1` 时，不展示差异摘要区
- 当最新版本主视图没有上一个版本可比较时，在概览卡里展示一句次级说明：`当前为首个版本，暂无历史差异可比`

## 7. 稳定结果提示区确认

稳定结果提示区是页面内常驻区域，不依赖全局 `message.success`。

它位于页面头部下方，并满足：

- 只有用户主动关闭或离开页面时才消失
- 不因自动刷新或轮询而消失
- 点击“查看版本历史”只改变页面内容，不清除提示本身

## 7.1 上传新版本成功

### 创建了新版本

展示内容：

- 标题：`已创建新版本 vN`
- 副标题：`上一版本为 vM，当前详情页已切换到最新版本`
- 事实字段：
  - `documentId`
  - `latestVersionNumber`
  - `previousVersionNumber`
  - 当前 `status`
  - 当前 `askableVersionNumber`
- 按钮：
  - `查看版本历史`
  - `去问答`，仅 `canAskNow = true` 时显示
  - `关闭提示`

### 同内容复用，未创建新版本

展示内容：

- 标题：`未创建新版本`
- 副标题：`上传文件与当前最新版本内容一致，当前仍停留在 vN`
- 按钮：
  - `查看版本历史`
  - `关闭提示`

不显示“去问答”按钮的条件：

- 当前不存在任何已 `INDEXED` 的可问答版本

此时要明确说明：

- `当前暂无可问答版本，请等待处理完成`

## 7.2 版本回退成功

展示内容：

- 标题：`已创建新的最新版本 vN`
- 副标题：`该版本回退自历史版本 vM`
- 事实字段：
  - `documentId`
  - `versionNumber`
  - `rollbackFromVersionNumber`
  - `latestVersionNumber`
  - `askableVersionNumber`
  - `versionOriginType = ROLLBACK`
- 按钮：
  - `查看版本历史`
  - `去问答`，仅存在可问答版本时显示
  - `关闭提示`

## 7.3 结果提示区的视觉语义

- 上传创建成功：绿色成功态
- 同内容复用：蓝色信息态，不当作警告
- 回退成功：琥珀色强调态，提醒用户该动作会影响最新版本语义与问答基线

## 8. 当前查看版本概览卡确认

概览卡要明确告诉用户“当前看的是谁”，而不只是罗列字段。

默认字段：

- `documentId`
- `knowledge base`
- `当前查看版本号`
- `系统当前最新版本号`
- `当前问答基线版本号`
- 当前查看版本 `status`
- `versionOriginType`
- 若为回退产生版本，显示 `回退自 vN`

补充说明规则：

- 当 `当前查看版本 != 系统当前最新版本` 时，显示橙色说明：`你正在查看历史版本，当前 document 最新版本为 vN`
- 当 `系统当前最新版本 != 当前问答基线版本` 时，显示橙色说明：`当前问答仍使用 vM，等待最新版本可用后才会切换`

## 9. 前端实现所需的数据契约补充

为避免前端靠二次推导拼状态，详情页接口至少需要提供以下字段。

后端契约落点：GitHub issue #20《版本历史只读后端查询接口》负责补齐 `versionHistory[]`
的只读查询能力。#3 前端只读视图不应基于 mock 数据或临时复用 status/list 接口推进。

## 9.1 详情主响应

建议前端消费的响应结构至少包含：

- `documentId`
- `kbId`
- `latestVersionNumber`
- `askableVersionNumber`
- `hasAskableVersion`
- `viewingVersionNumber`
- `canManageVersions`
- `canUploadNewVersion`
- `canRollbackVersions`
- `canDeleteDocument`
- `canReprocessLatestVersion`
- `latestStatus`
- `latestVersionOriginType`
- `versionHistory[]`

## 9.2 versionHistory 列表项

每一项至少包含：

- `versionNumber`
- `versionOriginType`
- `rollbackFromVersionNumber`
- `filename`
- `fileSize`
- `status`
- `failureReason`
- `createdAt`
- `updatedAt`
- `createdByUserId`
- `createdByDisplayName`
- `isLatestVersion`
- `isAskableVersion`
- `hasBeenRolledBackAsLatest`

## 9.3 成功结果 DTO

上传新版本成功结果至少返回：

- `documentId`
- `versionNumber`
- `previousVersionNumber`
- `latestVersionNumber`
- `askableVersionNumber`
- `status`
- `versionOriginType`
- `versionResultType`
- `versionCreated`

- `documentId`
- `versionNumber`
- `rollbackFromVersionNumber`
- `latestVersionNumber`
- `askableVersionNumber`
- `status`
- `versionOriginType`
- `canAskNow`

## 10. 验收对照

issue #2 的验收项与本文对应关系如下：

- 版本历史列表默认展示字段、排序方式、折叠规则和标记体系
  对应第 4 节
- 历史版本查看态与最新版本主视图的区分方式
  对应第 5 节与第 8 节
- 差异摘要区在详情页中的位置、摘要粒度和默认比较对象
  对应第 6 节
- 上传新版本、版本回退完成后的稳定结果提示区信息结构
  对应第 7 节
- 输出可以直接指导前端实现的交互确认结果
  对应第 3 节、第 8 节、第 9 节

## 11. 实施建议

实现顺序建议如下：

1. 先完成 #20 的版本历史只读后端契约，并补前端类型，确保 `latest version`、`askable version`、`viewing version` 三套事实可同时表达
2. 再把当前 `IngestStatusPage` 演进为真正的文档详情页
3. 最后接入上传新版本、回退成功后的稳定结果提示区

不要一开始就做复杂 diff 或动画；本 issue 的关键是把版本事实讲清楚，而不是把页面做得更炫。
