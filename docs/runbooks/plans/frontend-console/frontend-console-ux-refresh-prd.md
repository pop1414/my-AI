## 问题陈述

当前前端控制台已经覆盖文档上传、文档列表、知识库管理、问答、权限治理等主要能力，但整体体验仍然偏向按接口和模块堆叠，缺少统一的信息架构、稳定的共享页面骨架，以及与权限模型一致的角色视角。

从用户视角看，主要问题包括：

- 共享页面的主叙事不稳定。普通 `KB_READER` 在问答、知识库、文档详情等共享页面中，经常需要先穿过治理信息或技术化信息，才能完成“进入知识库、提问、核对依据、查看文档”的主任务。
- 管理角色的增强能力散落在页面各处，容易让页面呈现出“普通页面上再粘几个按钮”的感觉，既破坏普通成员体验，也让管理者缺少稳定的治理工作台感。
- 文档、知识库、问答三类核心页面缺少统一骨架，导致标题、摘要、操作区、空状态、错误态和加载态表现不一致。
- 当前前端对角色体验的表达不够精确。系统真实存在 `KB_READER`、`KB_CONTRIBUTOR / KB_MANAGER`、`WORKSPACE_ADMIN / WORKSPACE_OWNER` 三层体验，但页面容易退化成“普通用户 / 管理员”二分。
- 文档主链路仍不顺滑。文档列表、上传、详情、分块预览、重处理、删除之间的跳转与职责边界不够清晰，独立工具页偏多，普通成员和治理角色都需要频繁切换上下文。
- 正文读取专项 `#26-30` 尚未接入，因此当前前端优化如果不先把共享骨架和双视角规则定稳，后续正文视图接入时会继续返工。

如果继续在现有结构上局部补按钮和补样式，前端会越来越像多套半成品工作台的拼接：普通成员难以理解路径，治理角色难以形成稳定操作心智，后续正文读取、版本治理和权限增强也会持续放大这种割裂感。

## 解决方案

本次 PRD 聚焦“前端控制台体验重构与双视角收束”。目标不是立即接入正文读取专项，而是先把共享页面骨架、导航组织、角色视角和文档主链路整理稳定，为后续 `#26-30` 提供可落点的前端基础。

整体方案采用“外层模块型导航 + 页面内任务型编排”：

- 一级导航继续围绕稳定模块组织，例如 `文档`、`知识库`、`问答`、`系统管理`
- 进入页面后，信息组织围绕当前任务闭环展开，而不是继续把页面做成纯资源 CRUD 台账

共享页面遵守“同骨架、不同信息密度”原则：

- 同一个页面骨架在不同角色下保持一致，不为不同角色维护两套割裂页面
- 普通成员共享页面优先服务 `KB_READER` 的核对任务，例如选择知识库、提问、核对回答依据、查看文档当前上下文
- `KB_CONTRIBUTOR / KB_MANAGER` 在同一页面上获得更深一层的版本与文档治理能力
- `WORKSPACE_ADMIN / WORKSPACE_OWNER` 的系统治理能力主要集中在纯治理页面中表达，而不是继续把共享页面挤成治理杂糅面板

在 `document` 相关页面中，前端心智拆成“文档核对”与“文档治理”两个视角，但它们不是新的领域对象。普通成员面向文档核对视角，治理角色在同一详情页骨架中展开文档治理视角。问答页和知识库页同样优先围绕共享任务叙事组织，再对高权限角色补充治理增强层。

本期前端优化范围包括：

- 统一全局控制台骨架、设计 token、状态组件和共享页面结构
- 重构问答页与知识库页，使其首先服务普通成员的核对与进入任务
- 重构文档列表、上传页和文档详情外层工作台，明确“核对视角 / 治理视角”边界
- 收纳分块预览、状态查询、重处理、删除等工具页，减少主路径割裂
- 重构系统管理区域的治理体验，但保持其作为纯治理工作台，不强行复用普通成员页面叙事

本期不接入正文读取统一接口，不实现 `#26-30`，只为后续正文读取专项提供稳定页面骨架、共享状态组件、角色分区和入口语义。

## 用户故事

1. 作为 `KB_READER`，我希望知识库页面能帮助我快速选择一个 `knowledge base`，这样我可以不先穿过治理噪音就进入问答或核对任务。
2. 作为 `KB_READER`，我希望问答页首先围绕提问、回答和引用核对组织，而不是像调试面板一样堆接口信息。
3. 作为 `KB_READER`，我希望问答页持续清晰展示当前 `knowledge base` 上下文，这样我不会失去对回答来源边界的理解。
4. 作为 `KB_READER`，我希望文档详情页首先解释当前与问答相关的文档上下文，这样我可以核对内容，而不是先阅读治理元数据。
5. 作为 `KB_READER`，我希望文档相关共享页面保持只读且不杂乱，这样我不会被自己无权执行的动作干扰。
6. 作为 `KB_READER`，我希望空状态、加载态和错误态清晰且一致，这样我总能判断系统是在工作、等待还是不可用。
7. 作为 `KB_READER`，我希望文档列表更强调“适合核对/适合问答”的信息，而不是首先强调治理台账字段，这样我能更快选择目标文档。
8. 作为 `KB_READER`，我希望上传和治理类工具不要侵入我的主阅读路径，这样界面会更像工作台，而不是后台管理页。
9. 作为 `KB_CONTRIBUTOR`，我希望继续停留在与普通成员一致的共享页面骨架里，同时看到更深一层的版本与维护能力，这样页面会显得更深，而不是更裂。
10. 作为 `KB_CONTRIBUTOR`，我希望文档管理动作被稳定地归拢到治理区域，这样我能维护内容而不必在页面各处找按钮。
11. 作为 `KB_MANAGER`，我希望同一个文档详情页同时支持核对视角和治理视角，这样我不需要学习两套不同的文档页面。

14. 作为 `KB_MANAGER`，我希望文档列表和详情页比普通成员看到更多上下文，这样我能在主工作台里做版本和处理决策，而不是频繁跳页。
15. 作为 `WORKSPACE_ADMIN`，我希望共享页面继续保持任务导向，而成员、账号、授权、审计这些能力集中在独立治理页面中，这样系统治理不会压垮内容工作流。

17. 作为具备不同能力组合的用户，我希望权限不仅控制我能做什么，也控制我能看到多深的信息层级，这样界面才与我的真实边界一致。

## 实现决策

- 前端体验重构必须遵守 `ADR-0005` 与 `ADR-0006`，不得引入与已采纳权限边界或正文读取边界冲突的 UI 语义。
- 外层导航保持模块型组织，顶级入口继续围绕 `文档`、`知识库`、`问答`、`系统管理` 等稳定模块展开。
- 页面内部转为任务型编排。共享页面必须先支持当前用户的任务闭环，再对高权限角色展开更深治理信息。
- 共享页面统一使用页头、摘要/上下文区、主工作区和角色感知治理区的通用骨架。
- 需要引入统一的页面头部、操作簇、空状态、错误状态、加载状态与角色感知分区模型。
- 角色处理必须反映三层体验，而不是简单的二分：`KB_READER`、`KB_CONTRIBUTOR / KB_MANAGER`、`WORKSPACE_ADMIN / WORKSPACE_OWNER`。
- 共享页面必须遵守“同骨架、不同信息密度”规则，不再分化成两套独立的读者页和管理页。
- 治理能力应集中在稳定的治理区域中表达，例如页头操作区、治理侧栏或治理分区，而不是散落在基础内容区各处。
- `document` 在前端心智上拆成“文档核对 / 文档治理”，但这不是新的领域对象，也不改变后端资源模型。
- 文档详情页应成为表达这两个视角的核心页面；对具备治理能力的用户，应允许在同一详情页里切换或展开更深治理视角。
- 文档详情页保持稳定的四段式叙事：概览区、核对主区、版本/问答上下文区、治理区。
- 问答页围绕“提问 -> 回答 -> 核对引用”的叙事重构，并保持 `knowledge base` 上下文稳定可见；治理增强不能破坏这一主叙事。
- 知识库页围绕“选择 `knowledge base` 并进入下一任务”重构，而不是继续作为原始主数据表存在。
- 文档列表页要优先强调文档是否适合核对和问答，同时为高权限角色提供结构化治理入口。
- 上传页要被改造成连续文档工作流的一部分，上传完成后需要有明确的后续去向，而不是停留在技术表单状态。
- 当前的工具页集合需要降噪。分块预览可继续保持独立页；重处理、删除、状态查询应重新定位到文档主工作台周边。
- 纯治理页面如成员、账号、授权、审计应被整理成一致的治理工作区，而不是继续受读者页面叙事牵引。
- 本轮优先通过抽象共享深模块而不是逐页打补丁实现。关键共享模块包括 shell、header、toolbar、状态渲染、角色感知操作簇和角色感知分区。
- 本轮前端重构不改变正文读取 API 语义；`#26-30` 作为后续专项接入到本轮整理好的页面骨架之上。
- 本轮不清理 prototype 路由，不替换全局状态管理方案，也不在本期内重写后端契约。

## 测试决策

- 好的前端测试应验证外部可观察行为：可见结构、不同角色下的可见动作、页面状态切换和导航结果，而不是锁死 hook 组合或 Ant Design 具体 DOM 结构。
- 共享布局原语需要具备独立的组件测试，覆盖 loading、empty、error 和角色感知渲染分支。
- 问答页测试应验证其作为共享核对工作台的行为：`knowledge base` 上下文、回答流、引用区以及不破坏读者主叙事的治理增强。
- 知识库页测试应同时覆盖读者与治理角色，验证读者入口是否清晰、治理动作是否以结构化方式自然展开。
- 文档列表页测试应覆盖读者优先的默认理解路径，以及治理角色看到更多治理动作后的展开行为。
- 文档详情页测试是本轮最关键的共享页面测试，应覆盖读者核对优先、治理区域展开，以及跨角色仍保持同一页面骨架的一致性。
- 角色感知测试至少覆盖 `KB_READER`、`KB_CONTRIBUTOR / KB_MANAGER`、`WORKSPACE_ADMIN / WORKSPACE_OWNER` 这三类能力组合。
- 纯治理页面应独立测试为治理工作台，不强行套入读者叙事断言。
- 应优先复用现有登录页、文档列表、问答页、管理表格、路由守卫等现有前端测试风格，不另起一套无关模式。
- 因为本期明确排除 `#26-30`，所以正文读取语义、`source` 参数映射、正文读取权限文案等测试属于后续专项，而不是本轮前端重构范围。
