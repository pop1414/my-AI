# V1.1 规划草案

状态：Scope Adjusted（2026-05-08）  
基线版本：`v1.0.0`

## 1. 规划目标

V1 已经完成“能演示”的最小闭环。  
V1.1 的原始目标，是在现有闭环上补齐“更可持续使用”的基础管理能力。

截至 `2026-05-08`，V1.1 的范围已完成一次主动收缩：

- “知识库主数据化”已完成
- “文档列表与管理台”已完成
- 原计划中的“轻量认证与访问控制”不再作为 V1.1 收口项继续推进，而是独立拆出，升级为更完整的 RAG 权限体系专项
- 独立专项入口已落文为：
  - [RAG 权限体系专项计划](D:\Code\project\my-AI\docs\runbooks\plans\rag-access-control\rag-access-control-plan.md)
  - [ADR-0005：RAG 权限体系基础决策](D:\Code\project\my-AI\docs\adr\ADR-0005-rag-access-control-foundation.md)

一句话定义：

> V1.1 负责把管理基础盘打稳；权限体系单独成篇，不再用“轻量版补丁”方式并入收口。

## 2. 为什么当时要做 V1.1

从 `v1.0.0` 基线看，系统已经具备上传、状态查询、分块预览、重处理、删除、知识库展示和单轮问答能力，但当时仍存在三个明显短板：

1. 文档资产只有按 `documentId` 单点查询，缺少列表视角
2. 知识库仍停留在统计口径，还不是正式主数据
3. 控制台与 API 仍处于开放基线，没有清晰访问边界

其中前两项已经在当前阶段完成落地；第三项则不再用“先做个轻量鉴权顶上”的思路处理。

## 3. 当前基线判断

### 3.1 已完成的管理基础

- 已有独立 `knowledge_bases` 主数据表
- 已有知识库创建 / 列表 / 编辑接口
- 上传与问答链路已围绕正式 `kbId` 做存在性 / 状态校验
- 已有分页文档列表接口：`GET /api/v1/documents`
- 控制台默认落点已切换到 `/ingest/documents`
- 文档列表已成为 `ingest` 管理主入口

### 3.2 当前仍待专项规划的能力

- 尚未引入成熟的认证主数据
- 尚未定义角色、资源、作用域、授权决策链路
- 尚未把知识库 / 文档 / 分块预览 / 问答能力纳入统一权限模型

这说明下一阶段的核心问题已经不是“先临时封个入口”，而是“把权限方向一次规划对”。

## 4. V1.1 范围建议

当前建议把 V1.1 收敛为 2 个已完成主题，并把权限部分拆出为独立专项。

### 4.1 主题一：知识库主数据管理（已完成）

目标：把知识库从“统计口径”升级为“可维护对象”。

已落地能力：

- 知识库创建
- 知识库列表
- 知识库名称 / 描述 / 状态维护
- 上传与问答基于正式知识库做校验
- 前端知识库管理页与知识库选择器

价值判断：

- 它把 `kbId` 从约定字符串升级为正式主数据对象
- 它为后续权限绑定、配额治理、审计归属奠定了稳定对象边界

### 4.2 主题二：文档列表与管理台（已完成）

目标：把 V1 中零散的单点操作页，收拢为面向真实使用的文档管理入口。

已落地能力：

- 文档列表查询
- 按 `kbId / status / filename` 过滤
- 默认按 `createdAt DESC` 浏览
- 列表展示 `documentId / kbId / filename / fileSize / status / updatedAt`
- 行内跳转：
  - 查看状态
  - 分块预览
  - 重处理
  - 删除
- 前端已统一从 `/ingest/documents` 进入，并通过 URL 路径参数传递 `documentId`

价值判断：

- 它把当前控制台从“接口演示台”推进到“基础管理台”
- 它让文档资产开始具备集合视角，而不再只靠单点调试

### 4.3 独立专项：成熟 RAG 权限体系（从 V1.1 拆出）

目标：围绕真实 RAG 系统的对象边界和访问链路，单独规划一套可持续演进的权限体系，而不是仅做一次轻量入口封装。

专题入口：

- [RAG 权限体系专项计划](D:\Code\project\my-AI\docs\runbooks\plans\rag-access-control\rag-access-control-plan.md)
- [ADR-0005：RAG 权限体系基础决策](D:\Code\project\my-AI\docs\adr\ADR-0005-rag-access-control-foundation.md)

建议覆盖范围：

- 身份认证：登录、会话、令牌或网关接入策略
- 授权模型：用户 / 角色 / 资源 / 动作 / 作用域
- 资源边界：知识库、文档、分块预览、问答、重处理、删除
- 组织扩展位：为后续工作区、多团队、多租户预留演进方向
- 审计能力：谁在什么时间访问了什么资源、触发了什么操作

建议原则：

- 先画清楚资源与动作矩阵，再选技术实现
- 先定义知识库级与文档级边界，再决定是否下钻到分块和引用级
- 优先让权限体系服务后续演进，而不是只满足一次“先挡住入口”的短期诉求
- 首期安全基线需显式覆盖 CSRF 防护与登录暴力破解防护，而不是在工程落地时临时补想

## 5. 明确不并入 V1.1 的内容

以下内容建议继续放在 V1.1 之外或后续版本中独立推进：

- 成熟权限体系的具体实现
- 多租户隔离
- 复杂角色权限矩阵上线
- 多轮会话历史
- 聊天记录沉淀与导出
- OCR 与复杂版式增强
- 多模型切换与模型策略配置台

## 6. 推荐实施顺序

以当前状态回看，V1.1 的合理顺序应理解为：

1. 知识库主数据化
2. 文档列表与管理台
3. V1.1 文档收口
4. 独立启动 RAG 权限体系专项规划

原因：

- 先把 `kbId` 变成正式对象，后续所有绑定关系才有稳定锚点
- 再补文档列表，让文档资产管理从单点转为集合
- 最后不再把权限“硬塞进 V1.1”，而是基于前两项沉淀出的对象边界做完整规划

## 7. 建议拆分分支

V1.1 已完成部分可回看以下主题边界：

- `feature/knowledge-base-management`
- `feature/document-list`
- `feature/v1-1-closure`

权限专项建议单独命名，不再并入 `auth-v1-1` 这一类轻量分支语义，例如：

- `feature/rag-access-control`
- `feature/rag-auth-architecture`

## 8. 验收建议

当前 V1.1 收口时，建议至少满足以下条件：

1. 用户可以创建、编辑、启停知识库，而不是长期依赖手填 `kbId`
2. 用户可以在列表中看到文档资产，并完成查看、预览、重处理、删除
3. QA 仍能基于选定知识库完成单轮问答
4. README、Roadmap、API 契约与前端说明同步更新
5. 原“轻量认证与访问控制”已从 V1.1 范围显式拆出，避免形成隐性待办

## 9. 当前阶段建议动作

如果继续推进，建议下一步按这个顺序做：

1. 先完成 V1.1 文档真源收口
2. 单独补一份权限体系范围确认文档或 ADR
3. 先定义资源对象、角色边界和授权矩阵
4. 再决定采用何种认证 / 会话 / 授权落地方案

V1.1 现在应聚焦在两个词：

`收口、定边界`

而权限体系应该用另一套节奏推进：

`先设计对，再工程化`
