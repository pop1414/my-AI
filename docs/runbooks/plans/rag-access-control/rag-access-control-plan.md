# RAG 权限体系专项计划

状态：In Progress（2026-05-11）  
定位：独立专项规划（从 V1.1 拆出）  
基线版本：`v1.1` 管理基础收口后

## 1. 背景与目标

V1.1 已完成知识库主数据化与文档列表管理能力，系统已经具备：

- 正式的知识库主数据对象
- 文档集合视角与统一管理入口
- 基于知识库的上传与问答主链路

这意味着下一阶段的核心问题，已经不再是“先做一个轻量登录把入口封住”，而是：

> 围绕真实 RAG 系统的资源对象和访问链路，建立一套可持续演进的权限体系。

本专项的目标不是一次性落完整 SaaS 权限平台，而是先把方向和首期落地方案设计对，避免后续从轻量权限补丁返工。

## 1.1 当前实现现状（2026-05-11）

当前代码基线已经完成本专项的第一批工程化落地：

- 本地账号登录、登出、当前用户查询
- 基于服务端 Session 的认证态维护
- 工作区角色、知识库角色、文档覆盖三级授权
- 成员治理、知识库授权治理、文档授权治理、审计日志查询接口
- 业务链路接入权限判断：
  - 知识库创建 / 编辑
  - 文档上传 / 列表 / 状态 / 分块预览 / 重处理 / 删除
  - `qa.ask`
- 前端登录态恢复、管理员路由守卫与治理后台页面

当前仍未闭环的内容：

- 创建用户 / 禁用启用 / 重置密码 / 移除成员
- CSRF 从固定 Header 升级为动态 token

状态同步（2026-05-11，账号生命周期后端）：

- 创建用户 / 禁用启用 / 重置密码 / 移除成员的后端治理能力已完成
- 当前剩余未闭环项收敛为：
  - CSRF 从固定 Header 升级为动态 token
  - 前端账号管理页面接入
  - 前端知识库页 / 知识库选择器的联调验证

状态同步（2026-05-11，知识库列表可见性）：

- `GET /api/v1/knowledge-bases` 已完成列表可见性收紧
- 当前规则已固定为：
  - `WORKSPACE_OWNER / WORKSPACE_ADMIN` 返回当前工作区全部知识库
  - `WORKSPACE_MEMBER` 仅返回自己存在 `ACTIVE` 显式知识库授权的知识库
- 当前剩余未闭环项继续收敛为：
  - CSRF 从固定 Header 升级为动态 token
  - 前端账号管理页面接入
  - 前端知识库页 / 知识库选择器的联调验证

## 2. 范围边界

### 2.1 本专项要解决什么

- 定义首期认证模型与后续身份接入演进方向
- 定义工作区、知识库、文档、问答之间的授权边界
- 明确首期应该落地的数据模型、角色模型、授权优先级与安全基线
- 为未来升级到多工作区、多团队协作预留结构位

### 2.2 本专项当前不做什么

- 不在首期实现多租户隔离
- 不在首期接入真实企业 SSO / OIDC
- 不在首期落复杂组织树、审批流、计费与配额治理
- 不在首期把分块级权限作为一等授权对象

### 2.3 当前默认边界

- 单工作区优先
- 必须为后续多工作区升级预留模型空间
- 不允许把首期方案设计成仅适配单管理员的临时补丁

## 3. 首期身份与资源模型

### 3.1 身份模型

首期采用：

- 本地账号体系
- 服务端 Session 认证态
- `HttpOnly Cookie` 保存会话标识

同时在架构边界上预留未来接入：

- OIDC
- 企业 SSO
- Token / API Key 形态的系统调用能力

### 3.2 资源对象

首期需要纳入统一权限模型的资源对象：

- `workspace`
- `knowledge base`
- `document`
- `qa ask`

其中：

- `workspace` 首期虽然默认只有一个，但必须先入模
- `knowledge base` 是首期主要授权边界
- `document` 是对知识库授权的补充覆盖层
- `qa ask` 是受资源授权结果约束的业务动作，而不是独立脱离资源的权限点

### 3.3 数据模型方向

首期建议新增或补充的主数据：

- `workspaces`
- `users`
- `local_credentials`
- `workspace_memberships`
- `knowledge_base_grants`
- `document_grants`
- `audit_events`
- 登录失败计数 / 锁定状态相关字段或独立表

现有主业务表建议补充：

- `knowledge_bases.workspace_id`
- `ingest_documents.workspace_id`

并将历史数据回填到默认工作区。

## 4. 授权模型

### 4.1 工作区角色

首期建议固定 3 类工作区角色：

- `WORKSPACE_OWNER`
- `WORKSPACE_ADMIN`
- `WORKSPACE_MEMBER`

语义：

- `OWNER / ADMIN` 拥有系统治理、成员管理、授权管理、审计查看和全量资源访问能力
- `MEMBER` 不默认拥有全部内容访问权，需再叠加知识库或文档授权

### 4.2 知识库角色

首期建议固定 4 类知识库角色：

- `KB_MANAGER`
- `KB_CONTRIBUTOR`
- `KB_READER`
- `KB_ASKER`

建议能力边界：

- `KB_MANAGER`：知识库维护、授权管理、文档管理、问答
- `KB_CONTRIBUTOR`：上传、列表、状态、预览、重处理、问答
- `KB_READER`：列表、状态、预览、问答
- `KB_ASKER`：仅问答

### 4.3 文档级覆盖

首期建议支持文档级补充授权：

- `DOC_ALLOW_READ`
- `DOC_ALLOW_MANAGE`
- `DOC_DENY`

定位：

- 知识库级授权是主路径
- 文档级授权用于少量例外覆盖

### 4.4 授权优先级

首期建议采用以下优先级：

1. 未登录、账号停用、成员关系无效：直接拒绝
2. `WORKSPACE_OWNER / WORKSPACE_ADMIN`：直接放行
3. 先命中知识库级授权
4. 再应用文档级覆盖
5. `DOC_DENY` 优先级最高

## 5. RAG 特有权限规则

首期必须明确：

> `qa.ask` 只能检索和生成用户有权访问的文档内容。

这条规则需要同时约束：

- 检索候选范围
- Prompt 构造内容
- 最终返回的引用片段

不采用以下策略：

- 先用全知识库内容生成，再对引用结果裁剪

原因：

- 它会让权限边界和最终回答来源不一致
- 它不适合作为首期可解释、安全边界清晰的方案

## 6. 安全基线

### 6.1 CSRF 防护

首期采用：

- `Session + HttpOnly Cookie + SameSite + 自定义 Header`

规则：

- 写操作请求必须携带统一的自定义 Header
- 缺失或非法时后端直接拒绝
- `GET / HEAD / OPTIONS` 不要求该 Header
- 若未来部署拓扑需要放宽 `SameSite`，应通过配置而不是改语义

### 6.2 登录暴力破解防护

首期采用：

- 连续失败锁定

规则：

- 连续失败达到阈值 `N` 后短时锁定账号
- 锁定期间拒绝登录
- 登录成功后清空失败计数
- 管理员可手动解锁
- 登录成功、失败、锁定、解锁都进入审计事件

## 7. 首期 API / 数据表 / 接入点

### 7.1 认证接口

- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `GET /api/v1/auth/me`

### 7.2 后台治理接口

- 用户管理
- 知识库授权管理
- 文档授权管理
- 审计事件查询

### 7.3 现有业务接口接入点

现有链路需统一接入认证与授权判断：

- `knowledge-bases`
- `documents/upload`
- `documents`
- `documents/{id}/status`
- `documents/{id}/chunks/preview`
- `documents/{id}/reprocess`
- `documents/{id}`
- `qa/ask`

### 7.4 检索侧接入原则

首期建议采用：

- 先召回候选
- 再按用户实际可访问的知识库与文档过滤
- 过滤后的结果才允许进入生成链路

后续再评估是否把授权过滤进一步前推到向量检索层。

## 8. 验收标准

首期设计与实现完成时，至少应满足：

1. 用户能以本地账号登录、退出并查看自身身份信息
2. 工作区管理员能维护成员与授权关系
3. 知识库与文档接口能按角色边界正确放行或拒绝
4. `qa.ask` 不会使用无权文档内容生成回答
5. 审计中能回溯关键身份与授权操作
6. 当前模型在单工作区下可运行，并能平滑升级到多工作区

## 9. 后续阶段拆分

### 阶段一：方案定型

- 明确资源模型、角色模型、优先级规则
- 明确首期安全基线
- 完成 ADR 与专题计划沉淀

### 阶段二：首期工程化落地

- 引入安全框架
- 建立权限主数据
- 接入现有知识库、文档、问答链路
- 补前端最小后台与登录态处理

### 阶段三：能力增强

- 工作区扩展
- OIDC / SSO 接入
- API Token / 机器身份
- 更细粒度授权与治理能力

## 10. 一句话结论

这项专项的核心，不是“先给控制台加个登录框”，而是：

**围绕工作区、知识库、文档和问答链路，建立一套未来不用推倒重来的 RAG 权限基础盘。**
