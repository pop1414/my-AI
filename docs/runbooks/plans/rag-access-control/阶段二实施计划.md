# 阶段二实施设计清单

## 摘要

阶段二按“后端先行、正式迁移、Spring Security + Session”推进，目标是在不改动前端主流程的前提下，把认证、授权、审计和 `qa.ask` 权限边界落成可实现、可测试、可扩展的后端基线。
本阶段不做前端页面实现，只输出前端所需接口与状态约束；实现顺序固定为：迁移收口 -> 认证骨架 -> 授权主数据 -> 业务链路接入 -> 审计与验收。

## 关键实现清单

### 1. Schema 与迁移基线

- 引入正式迁移工具，默认选 `Flyway`，后续所有权限相关 schema 变更只走迁移脚本。
- 保留现有仓储读写方式，但停止在新权限模块中继续扩散“构造器内嵌 DDL”模式。
- 新增主数据表：
    - `workspaces`
    - `users`
    - `local_credentials`
    - `workspace_memberships`
    - `knowledge_base_grants`
    - `document_grants`
    - `audit_events`
    - `login_lock_states`（或等价独立表，承载失败计数/锁定到期时间）
- 补充现有表字段：
    - `knowledge_bases.workspace_id`
    - `ingest_documents.workspace_id`
- 迁移顺序固定：
    1. 建 `workspaces` 并插入默认工作区
    2. 给现有业务表补 `workspace_id`
    3. 回填历史 `knowledge_bases` / `ingest_documents` 到默认工作区
    4. 建权限与审计表
    5. 再补外键、唯一约束、必要索引
- 约束默认值：
    - 单工作区运行，但所有资源查询都显式带 `workspace_id`
    - `workspace_memberships` 对 `workspace_id + user_id` 唯一
    - `knowledge_base_grants` 对 `workspace_id + kb_id + user_id` 唯一
    - `document_grants` 对 `workspace_id + document_id + user_id` 唯一
- 索引最低要求：
    - `users.username`
    - `local_credentials.user_id`
    - `workspace_memberships(workspace_id, user_id)`
    - `knowledge_base_grants(workspace_id, kb_id, user_id)`
    - `document_grants(workspace_id, document_id, user_id)`
    - `audit_events(workspace_id, event_time desc)`

### 2. 认证与安全骨架

- 引入 `Spring Security`，采用服务端 `HttpSession`，首期 Session 存储使用容器内存，不引入 `spring-session-jdbc`。
- 认证模型固定为：
    - 用户通过本地账号登录
    - 登录成功后建立 Session
    - Session ID 通过 `HttpOnly Cookie` 下发
    - `GET/HEAD/OPTIONS` 允许无 CSRF Header
    - 所有写操作要求统一自定义 Header，例如 `X-CSRF-Token` 或团队约定名
- 安全链路固定：
    - 未登录访问受保护接口返回 `401`
    - 已登录但无权限返回 `403`
    - 账号停用、成员失效、账号锁定都视为认证或授权失败，不降级为业务 `400`
- 登录防暴力破解规则固定：
    - 连续失败计数按用户名维度累计
    - 达到阈值 `N` 后锁定 `T` 分钟
    - 成功登录清零
    - 锁定、解锁、成功、失败都写入审计
- 统一异常出口：
    - 增加全局异常处理，不再主要依赖控制器内联 `ResponseStatusException`
    - 统一返回 `ErrorResponse`，并补明确错误码，例如 `AUTH_REQUIRED`、`ACCESS_DENIED`、`ACCOUNT_LOCKED`

### 3. 授权模型与业务接入

- 工作区角色固定：
    - `WORKSPACE_OWNER`
    - `WORKSPACE_ADMIN`
    - `WORKSPACE_MEMBER`
- 知识库角色固定：
    - `KB_MANAGER`
    - `KB_CONTRIBUTOR`
    - `KB_READER`
    - `KB_ASKER`
- 文档覆盖固定：
    - `DOC_ALLOW_READ`
    - `DOC_ALLOW_MANAGE`
    - `DOC_DENY`
- 授权优先级固定：
    1. 未登录 / 账号停用 / 锁定 / 无有效 membership -> 拒绝
    2. `WORKSPACE_OWNER` / `WORKSPACE_ADMIN` -> 放行
    3. 命中知识库授权
    4. 应用文档级覆盖
    5. `DOC_DENY` 最高
- 后端实现方式固定：
    - 控制器不直接写权限判断
    - 应用层或独立授权服务负责“动作 + 资源 + 用户”判定
    - Repository/Query 层提供按可访问范围过滤的查询能力
- 现有接口接入顺序固定：
    1. `POST /api/v1/auth/login`
    2. `POST /api/v1/auth/logout`
    3. `GET /api/v1/auth/me`
    4. `GET/POST/PATCH /api/v1/knowledge-bases`
    5. `GET /api/v1/documents`
    6. `POST /api/v1/documents/upload`
    7. `GET /api/v1/documents/{id}/status`
    8. `GET /api/v1/documents/{id}/chunks/preview`
    9. `POST /api/v1/documents/{id}/reprocess`
    10. `DELETE /api/v1/documents/{id}`
    11. `POST /api/v1/qa/ask`
- 各业务动作默认映射：
    - 知识库列表/详情：至少 `KB_ASKER` 可见，是否可见停用库由工作区管理员全量可见、普通成员仅可见被授予资源决定
    - 上传/重处理/删除/授权管理：`KB_CONTRIBUTOR` 及以上，文档级 `DOC_ALLOW_MANAGE` 可放宽单文档管理
    - 文档状态/预览/列表：`KB_READER` 及以上，受 `DOC_DENY` 约束
    - `qa.ask`：`KB_ASKER` 及以上，且引用文档必须通过最终文档访问判定

### 4. RAG 检索与问答安全边界

- `qa.ask` 的权限过滤位置固定在“召回之后、生成之前”。
- 实现要求固定：
    - 先按 `kbId` 或默认知识库召回候选分块
    - 对候选分块按 `document_id` 做授权过滤
    - 只有过滤后的分块允许进入 Prompt 构造
    - 最终 `references` 只能来自同一批过滤后结果
- 明确禁止：
    - 先用全量召回结果生成回答，再裁剪引用
    - 仅在响应层过滤引用，不过滤生成输入
- 若过滤后无可用分块：
    - 返回正常问答响应，走“无命中/无可用内容”兜底，而不是返回 `403`

### 5. 审计与接口真源

- 审计事件最少覆盖：
    - 登录成功
    - 登录失败
    - 账号锁定
    - 账号解锁
    - 登出
    - 成员关系变更
    - 知识库授权变更
    - 文档授权变更
- `audit_events` 最低字段：
    - `event_id`
    - `workspace_id`
    - `actor_user_id`
    - `event_type`
    - `target_type`
    - `target_id`
    - `result`
    - `detail_json`
    - `event_time`
- 同步补齐 API 契约 `docs/04-api-contract.yaml`：
    - 新增 `auth` tag
    - 明确 `401/403/409` 使用场景
    - 为 `login/logout/me`、成员管理、知识库授权、文档授权、审计查询补请求响应 schema
    - 为现有 `knowledge/documents/qa` 接口增加认证与授权错误响应

## 对外接口与类型变更

- 新增认证接口：
    - `POST /api/v1/auth/login`
    - `POST /api/v1/auth/logout`
    - `GET /api/v1/auth/me`
- 新增后台治理接口：
    - 工作区成员管理
    - 知识库授权管理
    - 文档授权管理
    - 审计事件查询
- 现有接口行为变更：
    - 全部受保护业务接口默认要求登录
    - 原来部分 `400/409` 的权限语义改为 `401/403`
- 新增核心类型：
    - `AuthenticatedUser`
    - `WorkspaceMembership`
    - `KnowledgeBaseGrant`
    - `DocumentGrant`
    - `AuditEvent`
    - `LoginRequest` / `LoginResponse` / `MeResponse`

## 测试与验收场景

- 迁移测试：
    - 全新库初始化成功
    - 老数据回填到默认工作区成功
    - 重复执行迁移幂等
- 认证测试：
    - 正确账号登录成功并建立 Session
    - 错误密码累计失败后锁定
    - 锁定期间拒绝登录
    - 登出后 Session 失效
    - 写操作缺失 CSRF Header 返回 `403`
- 授权测试：
    - `WORKSPACE_ADMIN` 可访问全部资源
    - `WORKSPACE_MEMBER` 无 KB grant 时访问资源返回 `403`
    - `KB_READER` 可查列表/状态/预览，不可删除
    - `KB_CONTRIBUTOR` 可上传/重处理
    - `DOC_DENY` 能覆盖 KB 级允许
    - `DOC_ALLOW_MANAGE` 能放宽单文档管理
- RAG 测试：
    - `qa.ask` 不引用无权文档
    - 混合有权/无权召回候选时，只使用有权内容生成
    - 过滤后无结果时返回兜底回答
- 审计测试：
    - 登录成功/失败、锁定、授权变更均写入审计
    - 审计查询支持按时间和事件类型过滤
- 回归测试：
    - 现有知识库/文档/问答成功路径在登录后仍可工作
    - 现有控制器测试补充 `401/403` 分支

## 默认假设

- 本阶段只做后端设计与后端实现清单，不包含登录页和后台页面编码。
- 迁移工具默认选 `Flyway`，除非后续明确切换。
- Session 仅服务单实例本地/课程演示部署，不保证重启后保活。
- 单工作区仍是运行现实，但代码与数据模型必须显式携带 `workspace_id`。
- 不在本阶段引入 OIDC、SSO、API Token、多租户、分块级授权。
