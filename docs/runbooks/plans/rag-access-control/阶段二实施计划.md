# 阶段二实施设计清单

## 摘要

阶段二必须先新增一个 **0 号前置子阶段：DDL 收口与迁移接管**。
原因是当前仓库存在多处隐式/自动建表逻辑，如果直接引入 Flyway，应用启动会同时存在“代码自动改库”和“迁移脚本改库”两套机制，权限体系相关迁移无法稳定落地。

本阶段的固定技术路线为：

- 后端优先
- `Flyway` 全量接管 schema
- `Spring Security + HttpSession + HttpOnly Cookie`
- Session 首期使用容器内存
- 前端本轮不编码，只输出接口依赖

### 0. DDL 收口与迁移接管

- 引入 `Flyway`，将数据库结构变更切换为单一入口。
- 清除或禁用现有隐式 DDL 入口：
    - `JdbcKnowledgeBaseRepository` 构造器中的建表、索引、默认数据、回填逻辑
    - `JdbcDocumentRepository` 构造器中的建表、补字段、删索引、建索引逻辑
    - `spring.ai.vectorstore.pgvector.initialize-schema: true`
- 调整 `IngestSchemaVerifier`：
    - 去掉对 `JdbcDocumentRepository` 初始化顺序的隐式依赖
    - 保留“只读校验”职责，不再假设仓储会先自建表
- `vector_store` 和 `pgvector extension` 一并纳入 Flyway 管理，不保留框架自动建表例外区。
- 迁移脚本需覆盖现有业务表与向量表：
    - `knowledge_bases`
    - `ingest_documents`
    - `vector_store`
    - `pgvector extension`
- 第一批迁移目标不是加权限功能，而是把“现有数据库真源”从代码内嵌 DDL 平滑迁到 Flyway。
- 这一子阶段的完成标准：
    - 新库可仅靠 Flyway 启动成功
    - 关闭所有自动建表后应用仍能启动
    - 本地和测试环境不再依赖仓储构造器改库

### 1. 权限主数据与工作区入模

- 新增表：
    - `workspaces`
    - `users`
    - `local_credentials`
    - `workspace_memberships`
    - `knowledge_base_grants`
    - `document_grants`
    - `audit_events`
    - `login_lock_states`
- 给现有表补字段：
    - `knowledge_bases.workspace_id`
    - `ingest_documents.workspace_id`
- 历史数据迁移顺序固定：
    1. 创建默认工作区
    2. 回填 `knowledge_bases.workspace_id`
    3. 回填 `ingest_documents.workspace_id`
    4. 建立外键、唯一约束、索引
- 单工作区仍是运行现实，但所有主数据查询与授权判断必须显式带 `workspace_id`。

### 2. 认证与安全基线

- 使用 `Spring Security` 落本地账号登录。
- 新增接口：
    - `POST /api/v1/auth/login`
    - `POST /api/v1/auth/logout`
    - `GET /api/v1/auth/me`
- 认证行为固定：
    - 登录成功创建 Session
    - Session 通过 `HttpOnly Cookie` 维护
    - 未登录访问受保护接口返回 `401`
    - 已登录但无权限返回 `403`
- CSRF 基线固定：
    - `GET/HEAD/OPTIONS` 不要求 Header
    - 所有写操作必须带统一自定义 Header
- 防暴力破解固定：
    - 连续失败计数
    - 达阈值锁定
    - 登录成功清零
    - 成功/失败/锁定/解锁写审计

### 3. 授权模型与业务接入

- 工作区角色固定：
    - `WORKSPACE_OWNER`
    - `WORKSPACE_ADMIN`
    - `WORKSPACE_MEMBER`
- 知识库角色固定：
    - `KB_MANAGER`
    - `KB_CONTRIBUTOR`
    - `KB_READER`
    - `KB_ASKER`
- 文档覆盖固定：
    - `DOC_ALLOW_READ`
    - `DOC_ALLOW_MANAGE`
    - `DOC_DENY`
- 授权优先级固定：
    1. 未登录 / 账号停用 / 锁定 / membership 无效 -> 拒绝
    2. `OWNER/ADMIN` -> 放行
    3. 知识库授权
    4. 文档级覆盖
    5. `DOC_DENY` 最高
- 接入顺序固定：
    1. `knowledge-bases`
    2. `documents/upload`
    3. `documents`
    4. `documents/{id}/status`
    5. `documents/{id}/chunks/preview`
    6. `documents/{id}/reprocess`
    7. `documents/{id}`
    8. `qa/ask`
- 权限判断放在应用层授权服务，不把规则散落在控制器里。

### 4. RAG 检索边界与审计

- `qa.ask` 必须按“召回后、生成前”做文档访问过滤。
- 只有通过授权过滤的文档分块才能进入 Prompt。
- 最终引用片段只能来自同一批已授权候选。
- 过滤后无可用内容时返回问答兜底结果，不返回 `403`。
- 审计事件至少覆盖：
    - 登录成功
    - 登录失败
    - 账号锁定
    - 账号解锁
    - 登出
    - 成员变更
    - 知识库授权变更
    - 文档授权变更

### 5. 治理接口与后台运营

- 成员管理接口：
    - 查询工作区成员列表
    - 新增成员
    - 调整成员工作区角色
    - 停用或移除成员
- 知识库授权接口：
    - 查询 `knowledge_base_grants`
    - 授予或更新 `KB_MANAGER` / `KB_CONTRIBUTOR` / `KB_READER` / `KB_ASKER`
    - 回收知识库授权
- 文档授权接口：
    - 查询 `document_grants`
    - 授予或更新 `DOC_ALLOW_READ` / `DOC_ALLOW_MANAGE` / `DOC_DENY`
    - 回收文档级覆盖授权
- 审计查询接口：
    - 查询 `audit_events`
    - 支持按事件类型、成员、时间范围与资源维度过滤
- 治理接口阶段仍坚持后端优先，不在该阶段展开前端页面编码。

## 测试与验收

- DDL 收口测试：
    - 关闭所有自动建表后，新库可通过 Flyway 完整初始化
    - 旧库可平滑迁移，不依赖仓储构造器补字段
    - `vector_store` 可在关闭 `initialize-schema` 后正常工作
- 认证测试：
    - 登录成功、登出失效、锁定拒绝、写操作缺失 CSRF Header 返回 `403`
- 授权测试：
    - `ADMIN` 全量放行
    - `MEMBER` 无授权时 `403`
    - `KB_READER` 可读不可管
    - `KB_CONTRIBUTOR` 可上传/重处理
    - `DOC_DENY` 覆盖知识库允许
- RAG 测试：
    - `qa.ask` 不使用无权文档生成
    - 混合候选时只保留有权内容
    - 过滤后无结果时返回兜底答案
- 治理接口测试：
    - `OWNER/ADMIN` 可管理成员与授权
    - 普通成员访问治理接口返回 `403`
    - 授权变更后立即影响知识库、文档与问答链路
    - 成员变更、知识库授权变更、文档授权变更写入 `audit_events`
- 回归测试：
    - 知识库、文档、问答原有成功链路在登录后可继续工作

## 默认假设

- 本轮只做后端实施设计，不展开前端页面设计。
- Flyway 为唯一 schema 变更入口，不保留框架/仓储自动建表的长期并行机制。
- `schema-validation` 可保留，但前提是它只做校验、不做写入；若实际存在写行为，也纳入禁用范围。
- 不在本阶段引入 OIDC、SSO、API Token、多租户、分块级授权。
