# V1.1 规划草案

状态：Draft（2026-05-07）  
基线版本：`v1.0.0`

## 1. 规划目标

V1 已经完成“能演示”的最小闭环。  
V1.1 的目标不是再做一轮大而全扩张，而是在现有闭环上补齐“更可持续使用”的基础管理能力。

一句话定义：

> V1.1 要解决的是“V1 能跑通，但还不够好管、不够好用”的问题。

## 2. 为什么现在做 V1.1

从当前仓库状态看，V1 已具备上传、状态查询、分块预览、重处理、删除、知识库统计和单轮问答能力，但仍存在三个明显短板：

1. 文档资产只有按 `documentId` 单点查询，缺少列表视角
2. 知识库目前只是从 `ingest_documents` 聚合出来的统计结果，还不是正式主数据
3. 控制台与 API 仍处于开放基线，没有最小访问边界

这三个问题共同导致一个现状：

- 能演示
- 能联调
- 但不适合持续管理越来越多的文档和知识库

## 3. 当前基线判断

### 3.1 已有可复用基础

- `ingest_documents` 已持久化：
  - `kb_id`
  - `filename`
  - `file_size`
  - `status`
  - `failure_reason`
  - `retry_*`
  - `reprocess_*`
  - `created_at / updated_at`
- 这意味着“文档列表”所需的大部分字段已经存在，不一定要先大改表结构
- 当前 `qa` 与上传链路都已围绕 `kbId` 工作，知识库维度已经进入主业务路径

### 3.2 当前明显限制

- 当前没有独立的 `knowledge_bases` 主数据表
- 当前 `GET /api/v1/knowledge-bases` 只是基于 `ingest_documents` 的 `INDEXED` 聚合
- 当前控制台的“知识库管理”实质上还是只读统计页
- 当前没有用户、角色、登录、token 或 session 相关主数据与接口

这决定了 V1.1 不适合一上来就做复杂的多租户和权限体系，而应该先做“轻量可用版”。

## 4. V1.1 范围建议

建议 V1.1 只承载 3 个核心主题。

### 4.1 主题一：文档列表与管理台

目标：把 V1 中零散的单点操作页，收拢为一个面向真实使用的文档管理入口。

建议能力：

- 文档列表查询
- 按 `kbId / status / filename` 过滤
- 按创建时间倒序浏览
- 列表展示：
  - `documentId`
  - `kbId`
  - `filename`
  - `fileSize`
  - `status`
  - `updatedAt`
- 行内跳转或操作：
  - 查看状态
  - 分块预览
  - 重处理
  - 删除

后端建议：

- 新增文档列表接口，例如：`GET /api/v1/documents`
- 先做分页 + 条件过滤，不急着做复杂搜索
- 查询源优先复用 `ingest_documents`

前端建议：

- 新增正式“文档列表”页面
- 现有 `status / chunks-preview / reprocess / delete` 页面继续保留，但逐步转为从列表页进入

价值判断：

- 这是 V1.1 用户感知最强、收益最直接的一项
- 也是把当前控制台从“接口演示台”推进到“基础管理台”的关键一步

### 4.2 主题二：知识库主数据管理

目标：把知识库从“统计口径”升级为“可维护对象”。

建议能力：

- 知识库创建
- 知识库列表
- 知识库名称/描述维护
- 可选择是否允许停用知识库
- 上传时选择已有知识库，而不是主要依赖手填 `kbId`

后端建议：

- 引入独立 `knowledge_bases` 表
- `ingest_documents.kb_id` 与知识库主数据形成稳定关联
- 新增最小接口集，例如：
  - `POST /api/v1/knowledge-bases`
  - `GET /api/v1/knowledge-bases`
  - `PATCH /api/v1/knowledge-bases/{kbId}`
- 保留现有统计字段 `indexedDocumentCount`

兼容策略建议：

- 保留 `default` 作为历史兼容知识库
- 升级脚本初始化 `default`
- 上传和问答在 V1.1 期间仍允许默认回退，但 UI 不再鼓励手填裸 `kbId`

价值判断：

- 这是“知识库管理”从名义存在走向真实存在的关键补齐
- 也是后续多知识库、权限绑定、配额治理的前置基础

### 4.3 主题三：轻量认证与访问控制

目标：先给控制台与 API 加上最小访问边界，而不是直接做复杂权限系统。

建议能力：

- 登录 / 退出
- 单管理员账号，或极简用户表
- 控制台页面访问保护
- API 最小鉴权

建议边界：

- V1.1 只做“谁能进系统”
- 不做复杂 RBAC
- 不做租户隔离
- 不做文档级权限矩阵

技术策略建议：

- 优先评估 Spring Security 基线能力
- 认证方式可在 `session-cookie` 与 `token` 之间做一次小决策
- 无论选哪种方式，V1.1 都要避免把权限模型设计得过重

价值判断：

- 这一步的核心价值是“封住入口”
- 不是一次性解决企业级权限问题

## 5. 明确不并入 V1.1 的内容

以下内容建议继续放在 `V2 / V3`：

- 多租户隔离
- 复杂角色权限模型
- 多轮会话历史
- 聊天记录沉淀与导出
- OCR 与复杂版式增强
- 多模型切换与模型策略配置台

## 6. 推荐实施顺序

建议按下面顺序推进：

1. 知识库主数据化
2. 文档列表与管理台
3. 轻量认证与访问控制

原因：

- 先把 `kbId` 从“约定字符串”升级为“正式对象”，后续上传、列表、问答都会更稳定
- 文档列表直接承接现有 `ingest_documents` 数据，见效快
- 认证放在第三步更利于先把业务主路径打顺，再给入口加门

## 7. 建议拆分为 3 个执行分支

- `feature/knowledge-base-management`
- `feature/document-list`
- `feature/auth-v1-1`

如果想保留一个总收口分支，也可以额外建立：

- `feature/v1-1-closure`

## 8. 验收建议

V1.1 完成时，建议至少满足以下验收条件：

1. 用户可以登录后进入控制台
2. 用户可以创建或选择知识库，而不是长期依赖手填 `kbId`
3. 用户可以在列表中看到文档资产，并完成查看、预览、重处理、删除
4. QA 仍能基于选定知识库完成单轮问答
5. README、Roadmap、API 契约与前端说明同步更新

## 9. 当前阶段建议动作

如果继续推进，建议下一步按这个顺序做：

1. 先补一份 V1.1 范围确认文档或 ADR，敲定认证策略
2. 先实现知识库主数据层
3. 再落文档列表 API 与页面
4. 最后补登录与访问保护

## 10. 一句话结论

V1.1 不应该被做成“半个 V2”，而应该聚焦在三个词：

`可管理、可维护、有边界`
